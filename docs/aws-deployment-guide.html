Deploying to AWS

The first-timer path: one EC2 server, Docker Compose, and automatic HTTPS — the whole platform live on the internet in an afternoon, paid for entirely by the free credits your new AWS account came with. Everything scripted; every console click spelled out; no card charge possible on the Free plan.

route: EC2 + Compose + Caddy cost: $0 — runs on Free-plan credits credit burn: ~$1.20/day testing · ~$0.20/day parked time: ~2–3 hours first time prereq: docs/deployment-deep-dive.html Ch. 1–4

Overview

What you're building, and why this route

AWS offers a dozen ways to run containers. For a first deployment, almost all of them are the wrong choice: EKS (managed Kubernetes — what this repo's manifests ultimately target) costs ~$73/month before any servers and demands the full Kubernetes learning curve up front; ECS Fargate is simpler but hides Docker behind AWS-specific concepts. The beginner route is the classic one: rent one Linux server (EC2), run the same Docker Compose you already understand, and put Caddy in front for free automatic HTTPS. Everything you learned in the deployment deep-dive applies directly, and the skills transfer when you later graduate to EKS.

Know your account

The Free plan: your credit budget

AWS changed its free tier in July 2025. A new account like yours no longer gets "12 months of tiny free instances" — instead, at signup you chose the Free plan, which works like this:

  • $100 in credits the moment the account is created, spendable on almost any AWS service — including everything this guide uses (EC2, EBS storage, the public IP).
  • Up to $100 more for completing short "explore" activities in the console — launching an EC2 instance and creating a budget are two of them, and this guide has you do both anyway. Do the activities; it can double your testing time for free.
  • A hard time limit: the plan lasts 6 months or until the credits run out, whichever comes first. Note your signup date now and put a reminder at month 5.
  • No bill possible. A Free-plan account cannot charge your card. When credits or the 6 months are exhausted, the account simply stops and closes instead — so the classic beginner fear ("what if I forget something and get a $500 bill?") does not apply to you. The thing to protect is your credit balance, not your card.
  • The exit, in advance: when the plan ends, your resources stop. You then have a 90-day window to upgrade to the Paid (pay-as-you-go) plan and pick up exactly where you left off — leftover credits even carry over. After 90 days, AWS deletes everything. The "Before the free plan ends" section below turns this into a checklist so it never surprises you.
Where to watch the balance

Console → Billing and Cost Management → Credits shows the remaining amount and expiry. Glance at it after each testing week; with the routine below your burn rate will be so low that this becomes a formality. (If your account predates July 2025 it's on the old 12-month free tier instead — its always-free instances are 1 GB machines, too small for this stack, so the sizing advice here stays the same.)

The one habit that stretches $100 across months: an EC2 instance bills only while running, and this deployment is built to survive stops — data lives on the disk and in named volumes, the stack restarts itself on boot, and the Elastic IP keeps your DNS valid across stops. So: deploy once, and between testing sessions stop the server (~$0.20/day parked vs ~$1.20/day running). The exact click-path is in "The start–stop testing routine" below.

Step 0

First hour in AWS, safely

Never used AWS before? Three ideas orient everything: the console (the website) is where you click things; every resource lives in one region (a physical location you pick); and there are two kinds of login — the all-powerful root user (email + password you signed up with) and IAM users you create for daily work.

  1. Create the account at aws.amazon.com if you haven't — choose the Free plan when asked. (A card is required for identity verification, but on the Free plan it is never charged.)
  2. Secure the root user: IAM → root user → assign MFA device (your phone's authenticator app). Then stop using root for daily work.
  3. Create an admin IAM user: IAM → Users → Create user → name it, enable console access → attach the AdministratorAccess policy → enable MFA on it too. Log in as this user from now on.
  4. Create a budget (this is also one of the credit-earning activities): Billing and Cost Management → Budgets → Create budget → monthly cost budget of $20 with an email alert. On the Free plan this guards your credits; if you ever upgrade to Paid, it starts guarding your card.
  5. Do the "explore" activities on the console home / Free Tier page to unlock the extra credits — a few minutes each.
  6. Pick one region and stick to it — e.g. ap-south-1 (Mumbai, closest to you) or us-east-1 (usually cheapest). Resources are per-region; a "missing" instance is almost always the console showing the wrong region (top-right dropdown).

Step 1

Launch the server

Console → EC2 → Launch instance, then:

  1. Name: openrouter-prod
  2. AMI (operating system): Ubuntu Server 24.04 LTS, 64-bit x86.
  3. Instance type: t3.medium — the sweet spot for Free-plan credits. (Upgrade to t3.large later only if builds feel slow; it burns credits twice as fast.)
  4. Key pair: Create new → name openrouter-key → type ED25519 → .pem. The file downloads once — keep it; it's your SSH login.
  5. Network settings → Edit: create a security group named openrouter-sg with three inbound rules:
    • SSH (22) — Source: My IP (never 0.0.0.0/0 for SSH)
    • HTTP (80) — Source: Anywhere (0.0.0.0/0) — needed for certificate issuance + redirect
    • HTTPS (443) — Source: Anywhere (0.0.0.0/0)
    A security group is AWS's firewall — this is why the compose file never publishing database ports matters twice over.
  6. Storage: 30 GiB, gp3.
  7. Launch instance.

Then give it a permanent address: EC2 → Elastic IPs → Allocate → Allocate. Select it → Actions → Associate → pick your instance. Without this, the server's public IP changes on every stop/start and your DNS breaks.

Step 2

Point your domain at it

No domain? Two zero-to-cheap options

Free: DuckDNS (duckdns.org — sign in, claim a name like yourname.duckdns.org, set its IP to your Elastic IP). DuckDNS resolves any prefix of your name to the same IP, so api.yourname.duckdns.org and app.yourname.duckdns.org both work — just set DOMAIN=yourname.duckdns.org in .env.aws and skip the A-record table below. Fine for testing; not something to put in front of real users. Cheap and yours: a .xyz/.site-style domain from any registrar runs $2–4 for the first year and behaves exactly like the instructions below.

If you have a domain: at your DNS provider (wherever the domain lives — Namecheap, Cloudflare, Route 53…), create two A records pointing at the Elastic IP:

TypeNameValue
Aapi<your Elastic IP>
Aapp<your Elastic IP>

Verify propagation from your laptop before proceeding (both must return the Elastic IP):

laptop
nslookup api.yourdomain.com
nslookup app.yourdomain.com
Why this matters now

Caddy proves domain ownership to Let's Encrypt by answering a challenge on port 80. If DNS doesn't resolve to your server yet, certificate issuance fails (it retries automatically, but you'll stare at TLS errors in the meantime). If you use Cloudflare, set these two records to DNS only (grey cloud) until certificates are issued.

Step 3

Prepare the server

laptop
chmod 400 ~/Downloads/openrouter-key.pem
ssh -i ~/Downloads/openrouter-key.pem ubuntu@<ELASTIC-IP>

You're now on the server. Get the code up there. Easiest: push this repo to a private GitHub repository first, then clone it on the server (GitHub → your repo → Code → HTTPS URL; use a fine-grained personal access token as the password, or set up a deploy key):

server
git clone https://github.com/<you>/<repo>.git openrouter
cd openrouter
bash deploy/aws/setup-server.sh
# installs Docker + Compose, adds 4GB swap, enables Docker on boot.
# when it finishes: log out, then ssh back in (docker group takes effect on new login)
exit
Before you push to GitHub

The repo's .env contains a real leaked Google OAuth secret (GOCSPX-…). .env is gitignored so it won't be pushed — but rotate that credential anyway in Google Cloud Console, and run git status to confirm no .env* file is staged before your first push. .env.aws is also gitignored (added alongside this guide).

Step 4

Configure — one file

server — ~/openrouter
cp deploy/aws/.env.aws.example .env.aws
openssl rand -hex 32    # run three times — one output per secret below
nano .env.aws

Fill in, minimum:

  • DOMAIN — your bare domain (e.g. example.com; the stack serves api. and app. under it)
  • ACME_EMAIL — your email (Let's Encrypt expiry notices)
  • POSTGRES_PASSWORD, SECRET_KEY, NEXTAUTH_SECRET — one openssl rand -hex 32 output each
  • At least one LLM provider key (e.g. OPENAI_API_KEY) if you want real completions; OAuth and Stripe keys can wait.

Step 5

Deploy

server — ~/openrouter
./deploy/aws/deploy.sh

What happens, in order (all visible in the output): images build (~15–25 min the first time on a t3.medium — Go compile, pip install, Next.js build; cached and fast afterwards) → postgres/redis/nats start and pass healthchecks → the migrate one-shot runs alembic upgrade head and exits → backend, worker, beat, gateway, frontend start → Caddy starts, and on the first request to each hostname fetches its certificate. The script ends with container status and health checks.

Verify from your laptop:

laptop
curl https://api.yourdomain.com/health     # gateway says ok — with a valid certificate
# then open https://app.yourdomain.com in a browser

Congratulations — the platform is live on the internet. Take the moment; the first one only happens once.

The credit-saver

The start–stop testing routine

This is how you make $100 of credits last for your whole testing period. The deployment was designed for it: every service has restart: unless-stopped, Docker is enabled on boot, all data lives on the persistent disk, and the Elastic IP keeps your DNS pointing at the right place across stops.

Done testing for the day → stop the server

  1. EC2 console → Instances → select openrouter-prod.
  2. Instance state → Stop instance. (Stop, never Terminate — Terminate deletes the machine and its disk.)

While stopped you burn only ~$0.20/day (disk + reserved IP). The database, your .env.aws, built images, TLS certificates — everything — sits safely on the disk.

Ready to test again → start it

  1. Instance state → Start instance, wait 2–3 minutes.
  2. That's it. Docker starts on boot and brings the whole stack back by itself — no SSH needed. Verify from your laptop: curl https://api.yourdomain.com/health.
Why nothing breaks

The Elastic IP is the load-bearing piece: without it, every stop/start would hand the server a new public IP and your DNS records would point at a stranger. With it, the address — and therefore your domains and certificates — survives every stop. This is exactly why Step 1 allocated one.

Two habits that waste credits

(1) Forgetting the instance running overnight — harmless once (~$1), wasteful as a pattern; make stopping part of ending a session. (2) Orphaned resources: if you ever experiment beyond this guide, check EC2 → Instances and Elastic IPs in every region you've touched when cleaning up — an allocated-but-unattached Elastic IP quietly drains ~$3.65/month.

Troubleshooting

SymptomLikely cause → fix
Browser shows TLS/certificate errorDNS not propagated yet, or port 80 closed. Check nslookup, the security group, and … logs caddy for the ACME error.
backend restarts repeatedly… logs backend — usually a bad value in .env.aws (DSN password mismatch if you changed POSTGRES_PASSWORD after first boot: the DB keeps its original password inside the pgdata volume).
Build killed / server freezes during buildOut of memory on a small instance. The setup script's 4 GB swap prevents this; confirm with free -h. Worst case, build one service at a time: … build backend etc.
Frontend calls the wrong API URLNEXT_PUBLIC_* values are baked at build time. After changing DOMAIN, rebuild: … build frontend && … up -d frontend.
Disk fills up over timeOld image layers. docker system prune -f reclaims them (safe; running containers are untouched).
Can't SSH anymoreYour home IP changed and the security group pins SSH to the old one — edit the SSH rule's source in the console.
Credits draining faster than expectedSomething is running that you forgot. Check EC2 → Instances and Elastic IPs in every region you've used (top-right region dropdown), and Billing → Bills to see exactly which service is consuming credits.
Site unreachable after starting the instanceGive it the full 2–3 minutes; then … ps over SSH. If you're not using an Elastic IP, the public IP changed on stop/start and your DNS is stale — associate the Elastic IP from Step 1.

Security checklist

  • SSH restricted to your IP; login by key only (Ubuntu AMI default — no passwords).
  • Only 80/443 open to the world; databases unreachable from outside by two layers (no published ports + security group).
  • All secrets live in .env.aws, which is gitignored and exists only on the server.
  • Budget alert armed (guards your credits now, your card if you ever upgrade); MFA on root and your IAM user.
  • Nightly backup-db.sh in cron — a backup you've never restored is a hope, not a backup: test the restore command once.

Month 5

Before the free plan ends

The plan ends at 6 months or zero credits, whichever comes first — and then the account closes and resources stop. Handled a few weeks early, this is a non-event. The checklist:

  1. Check the runway: Billing and Cost Management → Credits (balance and expiry date).
  2. Get your data out, regardless of what you decide next:
    server, then laptop
    ./deploy/aws/backup-db.sh                       # on the server: dump the database
scp -i openrouter-key.pem ubuntu@<IP>:openrouter/backups/*.sql.gz .   # from your laptop
    Your code is already on GitHub and .env.aws is small enough to copy the same way — with those three things you can rebuild this deployment anywhere (any cloud, or a fresh AWS account) in under an hour.
  3. Then choose one:
    • Keep going on AWS: upgrade to the Paid plan (Billing → your plan → upgrade). Everything keeps running unchanged, leftover credits apply to your first bills, and from that moment the budget alert from Step 0 is guarding a real card — the start–stop routine now saves real money instead of credits.
    • Wind down: terminate the instance (Instance state → Terminate) and release the Elastic IP (Elastic IPs → Release). The account will close on its own; you have 90 days to change your mind by upgrading, after which AWS deletes what's left.

Later

When you outgrow one server

This setup honestly serves a surprising amount of traffic — thousands of users — and its ceiling is simple to raise first (resize the instance a size up; 5-minute downtime). The real limits are architectural: one machine is one failure domain, no autoscaling, deploys briefly restart services. When those start to hurt, this repo is unusually ready for the next step — it's what everything you've studied was built for:

  • Managed data first: move Postgres to RDS and Redis to ElastiCache (the Terraform in infrastructure/terraform/environments/dev/ already provisions both), point .env.aws at them, and the EC2 box becomes stateless and disposable.
  • Then EKS: the same Terraform stands up the cluster; your kustomize overlays and the minikube experience from the deep-dive labs transfer directly — push images to ECR, adjust the overlay image names, kubectl apply -k.

One honest caveat: this whole "later" path belongs to a Paid-plan account. An EKS control plane alone costs ~$73/month and RDS runs continuously — routes like that would drain a Free plan's credits in weeks. On free credits, the single server is the right architecture.
