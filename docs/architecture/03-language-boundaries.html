01 The dividing line

Three languages in one system is a real cost — three toolchains, three test setups, three sets of idioms for every new hire. It is only worth paying if the split buys something specific. Here it does, and the line is drawn in exactly one place.

The rule

Code that runs on every request is Go. Code that runs occasionally, slowly, or in the background is Python. Code that runs on someone else's machine is TypeScript.

And its enforcement clause: the Go gateway never opens a database connection. PostgreSQL belongs to Python alone.

1.1 Why that line and not another

The choice is driven by a latency budget, and the numbers make the argument on their own:

OperationCostConsequence
In-process map lookup~100 nsFree. Can happen on every request.
Redis round trip~500 µs5,000× a map lookup. Affordable once or twice per request.
PostgreSQL indexed query~1–5 ms10× Redis. Not affordable per request at 10k RPS.
argon2id verify~100 msDeliberately slow. Must never be on the hot path.
LLM first token~200–800 msDwarfs everything above.

The gateway's own overhead is roughly 150 µs of work plus whatever network hops it is forced to make. Put a database query on that path and the overhead grows by an order of magnitude — and, worse, couples gateway scaling to database connection limits. Two hundred gateway replicas each holding a Postgres pool would exhaust the database's connection ceiling long before the CPU noticed.

So the boundary is not aesthetic. It exists so that the two services can be scaled independently: the gateway on requests per second, the backend on database load.

1.2 What each language is actually good at here

LanguageThe property that earns it its placeWhat it would be bad at
Go Goroutines make I/O-bound concurrency nearly free — thousands of in-flight requests at ~2 KB of stack each, preemptively scheduled, with blocking-looking code. Plus predictable latency, trivial SSE streaming, and a 26 MB static binary that starts in milliseconds. Anything needing a rich library ecosystem. There is no Go equivalent of the provider SDKs, tiktoken, or Alembic.
Python The ecosystem. Every provider ships a Python SDK first; Stripe, tiktoken, SQLAlchemy, Alembic, Celery and the whole ML stack are mature here and nowhere else. The hot path. Cooperative async means one un-awaited CPU-bound call freezes every concurrent request on that worker.
TypeScript It is the language of the browser and of npm-distributed CLIs. There is no alternative for either target. Server-side hot paths, and anything needing real parallelism.

03 What Go owns

One sentence: everything between the client's socket and the provider's socket.

3.1 The concerns in detail

AreaWhat it doesGo-specific reason
Connection handlingAccepts client connections, spawns a goroutine per request, holds SSE streams open for the length of a generation.A 20-second stream costs ~2 KB of stack. A thread-per-request server would need megabytes each.
Auth cachingThree layers — in-process map, Redis, backend gRPC — with write-back and negative caching.The in-process layer only works if the process is long-lived and shared across requests, which rules out anything serverless.
Rate limitingPer-key sliding window, enforced identically across every replica.Not Go-specific; it is here because it must run before the provider call.
Routing & failoverModel → primary + fallback chain, each attempt wrapped in its own circuit breaker.atomic.Pointer gives lock-free config reads and hot reload with zero reader cost.
Protocol translationOpenAI shape ↔ provider shape, including a real SSE state machine for Anthropic.Streaming translation must be incremental and allocation-light; sync.Pool and byte slices make that natural.
Connection poolingOne tuned http.Client per provider, HTTP/2 forced.Saves ~300 ms of handshake per request. The default MaxIdleConnsPerHost of 2 would collapse throughput.

3.2 What Go is forbidden

  • No SQL. If you reach for database/sql in gateway-go/, the design has been violated. Ask Python.
  • No argon2. The gateway hashes with SHA-256 for lookup only; the memory-hard verification happens in Python, once, and is then cached.
  • No blocking work on the request path. Logging is one line at the end; telemetry is meant to go to a queue.
  • No business rules about money. The gateway carries a budget snapshot in the auth payload but never computes or deducts.
Reading the Go tree by responsibility

api/ is how the outside world reaches us — chain order, handler shapes, probe endpoints. service/ is what we decide — which provider, whether to allow, whether to trip. repository/ is who we talk to — Redis, the backend, the providers. If a change does not fit one of those three sentences, it probably belongs in Python.

04 What Python owns

One sentence: everything that must be remembered, priced, or computed with a library.

4.1 The four clusters

ClusterContainsWhy Python
System of record PostgreSQL schema and migrations, all eight tables, every repository, the Unit of Work. Exclusive ownership means one service reasons about transactions, one place defines the schema, and Alembic is the only thing that writes DDL.
Identity & money Key issuance with argon2, RBAC, audit logging, credit balances, atomic deduction, Stripe, the usage ledger, OAuth exchange. All of it is database-backed and none of it is per-request. The 100 ms argon2 cost is acceptable once per key, never per call.
Intelligence Model catalogue and pricing, semantic routing with capability and residency filtering, guardrail pipeline, token counting, the planned semantic cache. Needs pricing rows, tiktoken, and eventually embeddings and classifiers — none of which has a credible Go equivalent.
Asynchronous work Celery worker and beat: the video pipeline, HMAC-signed outbound webhooks, nightly billing aggregation. Durable, retried, long-running work that must survive process death. Celery plus Redis is mature here.

4.2 Python's two faces

The backend runs as two separate processes from one image, and the distinction matters:

  • FastAPI on :8000 serves humans and the frontend — key management, billing, OAuth, admin, webhooks. Scales on request rate.
  • gRPC on :50051 serves the gateway — ValidateKey and ResolveModel. Scales on auth cache-miss volume, which is a completely different curve.

Coupling them would mean over-provisioning one to serve the other. Splitting them is why app/grpc_main.py exists alongside app/main.py.

Where Python currently breaks its own rule

get_current_auth runs a 64 MB, ~100 ms argon2 verification inline on every authenticated backend request, with no cache. Go put three cache layers in front of this exact computation; Python put none. On a single-threaded event loop, that is the textbook cooperative-scheduling mistake — ten concurrent dashboard requests means 640 MB of hashing memory and a frozen loop. The fix is the same Redis cache the gateway already uses.

05 What the frontend owns

One sentence: everything a human needs to see, plus one server-side job nobody else can do.

5.1 The surfaces

SurfaceWhat it does
DashboardUsage overview, credit balance, spend charts. Composed of independently streaming <Suspense> boundaries so one slow query delays one card rather than the page.
Key managementCreate, list and revoke keys. Creation shows the plaintext exactly once, which is the only moment it exists outside a hash.
PlaygroundStreaming chat against any model, with a model picker and a code-snippet generator that emits working Python, TypeScript, curl and Go.
Model marketplaceCatalogue with pricing, modalities, filtering and comparison.
BillingBalance, top-up via Stripe Elements, usage history.
Marketing & docsLanding, pricing, changelog, status, MDX documentation.

5.2 The server-side job: the BFF

Why the frontend has a backend

The browser needs to call the gateway with a bearer token. Putting that token in client JavaScript exposes it to any XSS bug, any browser extension, and anyone who opens devtools.

So app/api/proxy/[...path]/route.ts sits in between. The browser authenticates to it with an httpOnly cookie — which JavaScript cannot read — and the server exchanges that for the real token before forwarding. The token never enters the browser. As a bonus the calls are same-origin, so there is no CORS preflight.

It streams upstream.body through unchanged, which is what keeps playground SSE working; buffering it there would silently break streaming.

5.3 Server versus client, inside the frontend

The frontend has its own internal boundary, and it is the same kind of decision as the Go/Python one:

Runs on the serverRuns in the browser
Page rendering (React Server Components are the default), data fetching with secrets, Server Actions for mutations, the BFF proxy, OAuth callbacks, session decoding. Anything needing useState, useEffect, event handlers or browser APIs — the theme toggle, the chat input, dialogs, the model filter.

The practical effect: a dashboard that is mostly text and tables ships almost no JavaScript, because server components send serialised UI rather than code.

06 What the CLI owns

Six commands — login, logout, models, chat, usage, keys — and one genuinely hard problem: storing a credential on someone else's laptop.

It solves that with the same Adapter pattern used for providers. KeytarStore uses the OS keychain (Keychain, Credential Manager, libsecret). When that is unavailable — headless servers, WSL, Alpine — EncryptedFileStore falls back to AES-256-GCM with a scrypt-derived key and mode 0600. Selection happens by probing: call keytar once and catch the failure, rather than guessing from the platform.

The CLI's real architectural value

It never talks to the backend, Redis or PostgreSQL. Every capability reaches it through the same public API a paying customer uses. That makes it the best available test that the public API is complete — if a feature cannot be done from the CLI, it cannot be done by a customer either.

07 Contested areas

Three places where the same concern exists in two languages. Two are deliberate; one is drift.

7.1 Provider adapters — in both deliberate, with a cost

gateway-go/internal/repository/adapters/ and backend-python/app/repository/providers/ both translate between the canonical shape and provider formats. They are not the same thing, and the difference is the justification:

Go adaptersPython adapters
Interface4 methods — normalise request, normalise response, stream translator, name6 methods — complete, stream, count_tokens, health_check, pricing, modalities
Built onRaw net/http and hand-written JSON structsThe official vendor SDKs
Used forServing live trafficToken counting, pricing, health scoring, and the catalogue
CoversOpenAI (+3 compatible), Anthropic, Google stubOpenAI, Anthropic, Gemma, Qwen

Why both. The Go adapter cannot call a Python SDK, and adding the SDKs to the hot path would mean a network hop to Python on every request — precisely what the architecture exists to avoid. Meanwhile the Python adapters answer questions the gateway never asks mid-request: what does this model cost, how many tokens is this prompt, is this provider healthy.

What it costs. Two implementations of "what Anthropic's wire format is" that can drift apart. If Anthropic changes its API, two files need editing, in two languages, and only one of them is exercised by live traffic — so the other rots silently. Nothing in CI checks that they agree.

The mitigation that makes it bearable

The overlap is kept small on purpose. Go implements only message translation; Python implements everything about a model. And OpenAI-compatible providers — Together, Fireworks, Ollama, and therefore Gemma and Qwen — need no translation at all on either side, which is why adding one is a config change rather than code. The genuine duplication is one provider: Anthropic.

7.2 Routing strategies — in both drift

gateway-go/internal/service/strategies/ has Cost and Latency behind a registry. backend-python/app/service/routing/strategies.py has Cost, Latency and Quality behind a registry. Same pattern, same names, two languages.

Unlike the adapters, this one has no defensible reason. The Go copy is never constructed — nothing builds the registry, so Router.Resolve returns the YAML order as written. It is a fully-formed abstraction that does nothing, while the Python copy does the real work behind ResolveModel.

The honest read

This is speculative abstraction: the pattern was built before the requirement arrived. Two reasonable resolutions exist. Either wire the Go copy and let the gateway rank its own fallback chain using pricing mirrored into Redis — which is what the PricingLookup interface was designed for — or delete it and let Python own ranking entirely, calling ResolveModel when a decision is needed. What should not persist is a second implementation that never runs.

7.3 Health checking — split awkwardly incomplete

Python's ProviderAdapter.health_check() returns latency and an error, and routing_servicer.ProviderScores converts p50 latency into a 0–1 score. Go's Latency strategy declares a ScoreLookup interface expecting exactly such scores. The contract between them exists in the proto.

Nothing connects the two. Python never runs health checks on a timer; Go never calls ProviderScores; the scores in routing.yaml are static operator-supplied numbers. The design is coherent and the wire is missing — the same shape of gap as the metering loop.

8.2 The "PROBLEM" branch is the interesting one

It is not a dead end — it is where the architecture's real decisions get made. Three escapes, all of which the codebase already uses:

EscapeMechanismExisting example
Cache itPython computes it, writes it to Redis; Go reads it. Accept bounded staleness.Auth metadata — 60 s TTL, which is also how long a revoked key keeps working.
Ask synchronouslyGo calls Python over gRPC, with a tight deadline, and caches the answer.ValidateKey on cache miss, 2 s deadline.
Defer itGo emits an event; Python consumes it out of band. The request does not wait.Usage events to NATS — designed, not yet built.

Which one to pick follows from a single question: what does a stale or missing answer cost? If staleness is merely suboptimal, cache it. If it is wrong — money, quotas, uniqueness — ask synchronously or keep it off the hot path. If nobody is waiting on the answer, defer it.

09 What the split costs

An honest accounting, because the benefits are stated everywhere else in these documents and the costs are not.

9.1 The recurring taxes

CostConcretely, in this repository
Contract maintenanceThree .proto files and an OpenAPI spec must stay correct, with codegen wired into every build. A fresh clone cannot compile until make proto runs.
Duplicated concepts"What an Anthropic request looks like" exists in two languages. So does the Strategy pattern. Nothing enforces agreement.
Four toolchainsGo modules, uv/pip, pnpm, npm — each with its own lockfile, test runner, linter and CI job.
Split debuggingA stack trace stops at the process boundary. Without working distributed tracing — which today is absent — following one request across services means correlating by hand.
OnboardingA contributor needs working knowledge of three languages to change anything end to end.
Deploy couplingA proto change requires deploying both sides, in an order that tolerates both versions running at once.

The four-layer convention described in document 1 is the main thing that repays the onboarding cost: whichever language a contributor lands in, the folders mean the same thing.

9.2 The boundary's biggest open question

Guardrails are on the wrong side of the line for their requirement

Guardrails need to inspect the prompt before it reaches a provider, and the response before it reaches the user. That is per-request, synchronous, and blocking — which by the rule in §01 makes it Go's work. But it needs ML classifiers, which makes it Python's.

The pipeline currently lives in Python with no caller. Three ways out, none free: run a classifier in Go via ONNX and accept a limited model; call Python synchronously and accept a per-request hop on a feature customers enable deliberately; or make it asynchronous and accept detection-after-the-fact rather than prevention.

This is worth naming rather than glossing over, because it is the one requirement the current split does not cleanly accommodate — and the choice should be made deliberately when the feature is built, not discovered during implementation.

9.3 Would a single language have been better?

Defensibly, yes, for a system at this stage. All-Python would be simpler to build and operate, and would hit a latency wall somewhere around a few thousand requests per second per replica. All-Go would be fast everywhere and would mean reimplementing tiktoken, writing provider clients by hand, and giving up the ML ecosystem entirely.

The polyglot split is a bet that the hot path will eventually matter enough to justify the tax. The right way to judge it is with the load tests in tools/load-tests/ and the metrics in shared/observability/ — and since no metric is currently recorded, the bet has not yet been evaluated. That, rather than any structural change, is the most valuable next piece of work.
