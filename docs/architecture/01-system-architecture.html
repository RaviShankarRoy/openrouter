01 What it is

An AI gateway. One OpenAI-compatible HTTP endpoint sits in front of many LLM providers. A customer points an existing SDK at it, changes nothing else, and can now call any model behind it.

Before — one integration per vendor          After — one integration, any model

  app ──► api.openai.com                       app ──► your gateway ──┬──► OpenAI
  app ──► api.anthropic.com                                          ├──► Anthropic
  app ──► generativelanguage.googleapis.com                          ├──► Fireworks (Gemma)
      3 SDKs, 3 keys, 3 bills                                        ├──► Together (Qwen)
      3 outage surfaces                                              └──► Ollama (self-host)
                                                               1 SDK, 1 key, 1 bill

The product is the compatibility, so the request and response shapes, the error envelope, and the streaming format all copy OpenAI's exactly. Everything the gateway adds — routing, failover, caching, rate limiting, metering — has to happen without changing that shape.

2.1 The one rule the topology enforces

The rule everything else follows from

The Go gateway never opens a database connection. PostgreSQL is owned exclusively by Python. Go gets what it needs from Redis, or by asking Python over gRPC, and then caches the answer.

Every structural oddity in this repository traces back to that sentence: the three-layer auth cache exists because Go cannot query the keys table; the gRPC contract exists because Go must ask someone; usage events go to a queue rather than an INSERT because Go cannot write rows; the model catalogue is proxied rather than served because pricing lives in Postgres.

The reason for the rule is a latency boundary, not fashion. The gateway runs on every request and is scaled on requests per second; the backend runs occasionally and is scaled on database load. Letting the hot path touch the database would couple those two scaling decisions together and put a 1–5 ms query on a path budgeted in microseconds.

Why this is worth the consistency

A developer who has read one service can navigate the other three without learning a second vocabulary. "Where is the Stripe client?" has the same answer shape in every language: repository/. "Where is the rule about what a revoked key means?" is always service/. Onboarding cost drops from four mental models to one.

The trade-off is that the names are slightly unusual outside Go. A Python developer would ordinarily expect infrastructure/; a React developer would expect components/. The repository pays that small unfamiliarity once to get uniformity everywhere.

Where the naming leaks

In the frontend, src/api/ holds React components rather than an API surface, which reads oddly — it is the delivery layer for a browser, so the position is right but the word does extra work. And src/app/ (Next.js routing, imposed by the framework) sits alongside it, so the frontend actually has five top-level folders rather than four.

05 Request lifecycle

One POST /api/v1/chat/completions, warm path. This is the spine of the system.

#StageLayerWhat happens
1RequestIDapiReads X-Request-ID or mints a UUID; stores it in context and echoes it on the response.
2RecovererapiDeferred recover() turns a panic into a 500 rather than killing the worker.
3LoggerapiWraps the writer to capture the status; the line is written on the way out, never the body.
4TracingapiOpens an OpenTelemetry span.
5Authapi → repositorySHA-256 of the bearer token, then in-process map (~100 ns) → Redis (~500 µs) → backend gRPC (~10 ms). Result written back up every layer. Unknown keys are negatively cached.
6RateLimitapi → serviceOne atomic Redis Lua script implements a sliding window over a sorted set. Emits the three X-RateLimit-* headers; 429 with Retry-After on rejection.
7HandlerapiBody capped at 10 MB, parsed for just model and stream. Non-streaming requests check the L1 cache keyed on SHA-256(model ‖ 0x00 ‖ body).
8RouterserviceModel id → primary provider plus an ordered fallback chain. Config is read through an atomic.Pointer, so this is lock-free and hot-swappable on SIGHUP.
9CircuitBreakerserviceOne breaker per (provider, model). Five consecutive failures opens it for 30 s, then three half-open probes.
10AdapterrepositoryCanonical OpenAI shape → provider-native. OpenAI-compatible providers pass through; Anthropic gets a genuine rewrite.
11Provider callrepositoryPer-provider pooled http.Client, HTTP/2 forced, keep-alive. 5xx and 429 count as failures and feed the breaker.
12ResponseserviceBuffered: read, normalise, write. Streaming: 32 KB pooled buffer through a per-request SSE translator, flushed after every chunk.
13Telemetry—not built Designed to publish a UsageEvent to NATS off the request path.
14Metering—not built Python would price the event, deduct credits atomically, and append a usage row.

Steps 1–12 are implemented and compile. Steps 13–14 have every component written — the proto message, the event bus, the billing service, the Celery tasks — but nothing publishes the event, so the loop between usage and money is open. See §12.

5.1 The two paths that leave Go

  • model: "openrouter/auto" — should call Python's RoutingService.ResolveModel, which filters a candidate pool by capability, geography and data residency, then ranks it by cost, latency or quality. The Python side is written; the Go side does not call it yet.
  • Video jobs and the model catalogue — delegate entirely to the backend. Currently stubbed in Go, returning 501.

7.1 Two design decisions worth understanding

The two-hash API key

Each key is stored twice. argon2id in key_hash — memory-hard at 64 MB, deliberately slow, the defence if the database leaks. SHA-256 in key_lookup — fast, deterministic, unique, indexed.

You need both because argon2 is salted, so the same key hashes differently every time and can never serve as an index. Validation is therefore: SHA-256 → one index seek → one argon2 verify against the single candidate. You get a memory-hard hash without paying for it on lookup.

This is safe because API keys are 256 bits of machine-generated entropy — the fast hash is not brute-forceable. The same pattern applied to human-chosen passwords would be broken.

Money is never read-modify-written 
UPDATE credit_balances
   SET available = available - :amount
 WHERE org_id = :org_id
   AND available >= :amount     -- the invariant, enforced by the database
-- rowcount == 0  →  insufficient funds

The check lives inside the write, the arithmetic is relative rather than absolute, and PostgreSQL locks the row for the duration. Two concurrent deductions cannot both pass. The naive read-check-write version loses updates, which is the single most common billing bug.

The reserved column supports the two-phase variant — hold an estimate before a provider call, settle the real cost after — so two expensive concurrent requests cannot both pass a balance check on the same funds.

providers.yaml stores key_env: ANTHROPIC_API_KEY, and the adapter does os.Getenv(cfg.KeyEnv) at request time. That is what lets the file be committed to git and mounted as a ConfigMap while the value arrives separately as a Secret.

09 Observability

The conventions are sound on paper: JSON to stdout with UTC timestamps, metric names shaped {service}_{subsystem}_{metric}_{unit}, and deliberate cardinality discipline — labels are limited to model, provider, status, cache_hit, never user_id or request_id, because series count is the product of label cardinalities.

The observability layer is the weakest part of the system

All seven Go collectors are declared and registered, and none is ever incremented — /metrics serves Go runtime statistics only. No OTel propagator is registered and neither outbound client is instrumented, so the gateway emits orphan spans and Python emits a separate trace; the two never join. X-Request-ID is minted, logged and returned, but never forwarded to the provider or over gRPC.

The compounding effect is what matters: the rate limiter fails open silently, circuit breakers trip silently, fallbacks fire silently, and the cache hit rate is unknowable. Every reliability mechanism described in this document is currently invisible in production. It is also the cheapest thing on the fix list — the call sites already exist.

10.1 What the Kubernetes manifests actually encode

The manifests are unusually complete, and every non-obvious choice carries a comment explaining itself. The decisions worth knowing:

  • Pod Security Standards "restricted" — non-root uid 65532, read-only root filesystem, all Linux capabilities dropped, seccompProfile: RuntimeDefault, with explicit emptyDir mounts for the paths that genuinely need writes.
  • Topology spread constraints across zone and hostname, so one availability-zone failure cannot take every replica.
  • Three probe types. Startup suppresses the others during boot; liveness never checks dependencies (or a Redis blip restarts the fleet); readiness does, so an unhealthy pod leaves the load balancer without being killed.
  • A preStop sleep of 5 s before SIGTERM. Endpoint removal and SIGTERM race; the sleep lets endpoint propagation win, which is what prevents 502s on every rollout.
  • No CPU limit on the gateway, deliberately. CFS quota throttling stops a container dead for the rest of its 100 ms period, which destroys tail latency while CPU graphs still look calm.
  • HPA v2 on a custom RPS metric plus CPU plus memory, with asymmetric behaviour — 30 s stabilisation scaling up, 300 s scaling down.
The base is not directly applicable on minikube

Base ships ExternalSecret CRs pointing at Vault, ServiceMonitor and PrometheusRule CRs requiring the Prometheus Operator, and a Spilo/Patroni StatefulSet that reads a bootstrap secret nothing in the repository creates. The minikube overlay exists precisely to strip all four and substitute plain Secrets and a plain pgvector/pgvector:pg16 container. Use that overlay, not dev, on a laptop.

12.3 Deliberately future work

Marked as later phases in the plan and correctly stubbed rather than half-built: Stripe beyond PaymentIntent creation, the Celery video pipeline bodies, ML-based guardrails (presidio, llm-guard), the pgvector semantic cache, the MCP server and client, and 56 of the 60 planned provider adapters.

If you want to make this real, in this order
  1. Record the metrics that already exist. A handful of one-line calls at sites that are already there. Everything after this becomes verifiable instead of hopeful.
  2. Register the OTel propagator and instrument the two clients. Turns two orphan traces into one waterfall.
  3. Call register_providers() in the FastAPI lifespan. One line; makes the model catalogue real.
  4. Write the L1 cache after a successful non-streaming response, asynchronously and with context.Background() so request cancellation does not abort the write.
  5. Stop failing over once the response is committed. Track it in the proxy loop.
  6. Publish the usage event and consume it. This closes the loop between traffic and money, and is the largest single piece of remaining work.
