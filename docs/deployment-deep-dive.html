Chapter 1

Why containers exist

The problem Docker solves

Imagine handing this repo's Python backend to a friend. For it to run, their machine needs: Python 3.12 exactly, the libpq5 system library for Postgres, ~40 pip packages at the exact versions in the lockfile, the right environment variables, and a working directory laid out just so. If any piece differs — Python 3.11, a missing system library, a newer package — it breaks, and you get the oldest sentence in software: "but it works on my machine."

A container ends that sentence. It bundles the application together with its entire userspace world — the OS files, the language runtime, the libraries, the exact dependency versions — into one sealed, portable unit. The unit runs identically on your laptop, your friend's laptop, and a cloud server, because everything it needs travels inside it. The only thing it borrows from the host is the Linux kernel itself.

Container vs virtual machine

You may have used VirtualBox or a cloud VM. A virtual machine emulates an entire computer — virtual CPU, virtual disk, and a full guest operating system with its own kernel. That's heavy: gigabytes of disk, minutes to boot, and a whole OS to patch per VM.

A container is much lighter. It is just a normal Linux process on the host, but wrapped in two kernel features: namespaces (the process gets its own private view of the filesystem, network, process list, hostname — it genuinely cannot see the rest of your machine) and cgroups (the kernel caps how much CPU and memory it may use). No guest OS, no emulation. That's why a container starts in milliseconds and why this repo's Go gateway image is under 30 MB while a VM doing the same job would be gigabytes.

Virtual machine vs container

VM: App → Guest OS → Hypervisor → Host OS → Hardware
Container: App (+ its libraries) → shared Host kernel → Hardware

What "Docker" actually is

Docker is four things that people blur into one word:

  • The Docker daemon (dockerd) — a background service on your machine that builds images and runs containers.
  • The Docker CLI (docker) — the command you type; it just sends requests to the daemon.
  • The image format — the standardized package (now an open standard, OCI) that any container tool can run.
  • The registry — a server that stores and serves images, like GitHub for code. Docker Hub is the default public one; this repo's manifests reference a private one, ghcr.io (GitHub Container Registry).
Try it now

Your machine already has Docker 29.7. Prove the whole pipeline works in one command:

shell
docker run hello-world

Unpack what just happened: the CLI asked the daemon to run an image called hello-world; the daemon didn't have it locally, so it pulled it from Docker Hub, created a container from it, ran its program (which prints the message), and the container exited. Now try an interactive one — a full Python environment you never installed:

shell
docker run -it --rm python:3.12-slim python
# you're now inside a Python 3.12 REPL running in a container.
# type exit() — the --rm flag deletes the container when it exits.

-i keeps stdin open, -t gives you a terminal, --rm cleans up afterwards. That python:3.12-slim image is the exact base this repo's backend is built on.

Chapter 2

Images, containers, layers

Image vs container — the one distinction that matters

An image is a frozen, read-only snapshot: a complete filesystem (OS files + your app + its dependencies) plus metadata (which command to run, which user, which ports it expects). It's a recipe result, sitting on disk, doing nothing.

A container is a running instance of an image — the image's filesystem brought to life as a process, plus a thin writable layer on top for anything the process writes. One image can spawn many containers, the same way one class spawns many objects, or one .exe can be launched many times. Delete a container and the image is untouched; anything the container wrote (that wasn't in a volume — Chapter 4) is gone with it.

Names and tags

An image name like ghcr.io/openrouter/backend-python:0.1.0 reads right-to-left: tag 0.1.0 (a version label), repository backend-python, namespace openrouter, registry ghcr.io. Omit the registry and Docker Hub is assumed; omit the tag and :latest is assumed. One crucial fact for later: tags are mutable — whoever controls the registry can re-point :0.1.0 at different content tomorrow. A digest (@sha256:…) is the content's cryptographic hash and can never silently change. This repo's production overlay pins digests for exactly that reason (Chapter 7).

Layers — why builds are fast the second time

An image isn't one big blob. It's a stack of layers, where each layer is the filesystem diff produced by one build step. Layers are content-addressed and shared: if five images all start from python:3.12-slim, that base is stored once on disk and downloaded once. And when an image is rebuilt, any step whose inputs haven't changed reuses its cached layer instead of re-running. Nearly every design decision in this repo's Dockerfiles is arranged around this cache — you'll see it in Chapter 3 and feel it in Lab 1.

The lifecycle

Image lifecycle

Dockerfile
→ build →
image
→ tag / push →
registry
→ pull →
container

You build an image from a Dockerfile, tag it with a name, push it to a registry, and any machine anywhere can pull and run it. That last hop — a server pulling an image and running it — is, at heart, all Kubernetes does, just automated across many servers with a lot of judgment attached.

Try it now
shell
docker image ls                     # images on your disk (the frozen snapshots)
docker ps                           # RUNNING containers
docker ps -a                        # includes exited ones — see your dead hello-world?
docker history python:3.12-slim     # the layer stack of the image, biggest steps visible
docker container prune              # delete all exited containers (images stay)

Chapter 3

The Dockerfile, line by line

A Dockerfile is the build recipe: a plain-text list of instructions the daemon executes top to bottom, each producing one layer. Before reading this repo's three, learn the instruction vocabulary once:

FROM <image>
Start from an existing image as the base. Every Dockerfile begins here. FROM x AS name names a stage — more below.
WORKDIR /path
Set the current directory for all following instructions (creates it if missing).
COPY src dst
Copy files from your project folder (the "build context") into the image. COPY --from=stage copies from an earlier build stage instead.
RUN <command>
Execute a shell command at build time (install packages, compile code) and bake the result into a layer.
ENV KEY=value
Set an environment variable that will exist inside every container run from this image.
ARG KEY=default
A build-time-only variable, passed with docker build --build-arg. Unlike ENV, it doesn't exist in the running container.
EXPOSE 8080
Pure documentation: "this app listens on 8080." It does not open the port — publishing ports happens at run time (-p 8080:8080).
USER 65532
Which user the container's process runs as. Default is root — fine at build time, a real risk at run time, hence every image here switches to an unprivileged user.
ENTRYPOINT / CMD
What runs when the container starts. Rule of thumb: ENTRYPOINT is the fixed program, CMD is its default arguments (or the default command if no ENTRYPOINT). docker run image something-else overrides CMD but not ENTRYPOINT — which is why Kubernetes can reuse one backend image for three different workloads later.
HEALTHCHECK
A command Docker runs periodically inside the container to decide if it's "healthy". Compose can wait on it. (Foreshadowing: Kubernetes ignores this entirely and brings its own mechanism.)
Concept · multi-stage builds

Building software needs heavy tools — compilers, headers, package managers. Running it doesn't. A multi-stage build uses one stage (with all the tools) to compile, then starts a fresh, minimal final stage and copies in only the finished output. The tools never ship. Every production image in this repo does this; it's the single most important Dockerfile pattern.

3.1 · gateway-go/Dockerfile — the minimal extreme

gateway-go/Dockerfile (annotated)
FROM golang:1.24-alpine AS build   # stage 1: has the whole Go toolchain
WORKDIR /src
COPY go.mod go.sum ./              # dependency lists FIRST…
RUN go mod download                # …so this slow download layer caches
COPY . .                           # source LAST — edits only invalidate from here down
ARG VERSION=dev
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -trimpath -ldflags "-s -w -X main.version=${VERSION}" \
    -o /out/gateway ./cmd/gateway

FROM scratch                       # stage 2: literally an EMPTY filesystem
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/gateway /gateway
COPY --from=build /src/configs /configs
EXPOSE 8080 9091
USER 65532:65532
ENTRYPOINT ["/gateway"]

What each decision means, and why:

  • Why copy go.mod/go.sum before the source? The layer cache. Dependencies change rarely; source changes constantly. Ordered this way, editing a .go file skips the download layer entirely on rebuild. Reversed, every rebuild would re-download every module. This deps-then-source order appears in all three Dockerfiles — it is the build-speed lever.
  • Why CGO_ENABLED=0? It tells Go to produce a fully static binary — one file containing everything, no dependency on the C library. That's what makes the next line possible.
  • Why FROM scratch? scratch is a zero-byte base — no shell, no package manager, no OS files at all. Only a static binary can survive there. The payoff: a final image under 30 MB, near-instant pulls, and essentially nothing for an attacker to use (you can't even open a shell in it — Lab 6 shows the Kubernetes trick for debugging such a container).
  • Why copy CA certificates? Because scratch has nothing — including the root certificates every HTTPS client needs to verify servers. Without this line, the gateway's outbound TLS calls to OpenAI/Anthropic would fail. The classic scratch-image gotcha.
  • Why -ldflags "-s -w" and -X main.version? -s -w strips debug symbols (smaller binary). -X writes a value into a Go variable at compile time — combined with ARG VERSION, CI stamps each build with its release version without touching code.
  • Why USER 65532, a bare number? Containers run as root unless told otherwise; if a process is compromised, root inside the container is a much better beachhead than an unprivileged user. 65532 is the conventional "nonroot" UID from Google's distroless images. It's numeric on purpose: Kubernetes' runAsNonRoot check (Chapter 6) can only verify a numeric UID — with a named user it can't prove non-rootness.

3.2 · backend-python/Dockerfile — the builder-venv pattern

backend-python/Dockerfile (annotated)
FROM python:3.12-slim AS builder
RUN apt-get install … build-essential gcc libpq-dev   # compilers + Postgres headers
RUN python -m venv /opt/venv                          # isolated env at a known path
ENV PATH="/opt/venv/bin:$PATH"
COPY pyproject.toml ./
RUN pip install -e .                                  # deps first (cache, again)
COPY . .

FROM python:3.12-slim AS runtime
RUN apt-get install … libpq5 curl && useradd --uid 65532 … app
COPY --from=builder /opt/venv /opt/venv               # finished packages only
COPY --from=builder /build /app
USER 65532
HEALTHCHECK --interval=10s … CMD curl -fsS http://localhost:8000/health
CMD ["gunicorn", "app.main:app", "--workers", "4", …]

Python can't compile to one static file, so the trick is different: build all the packages in a stage that has compilers, into a virtualenv at a fixed path, then copy just that venv into a clean stage. Notice the mirror-image pair: the builder installs libpq-dev (headers, needed to compile the Postgres driver), the runtime installs only libpq5 (the shared library needed to run it). No compiler ever ships to production.

  • PYTHONUNBUFFERED=1 makes print/log output flush immediately instead of buffering — without it, docker logs shows nothing until 4 KB accumulates, which reads as "my app is hung" when it isn't.
  • The HEALTHCHECK is why curl is installed in the runtime at all — a deliberate trade of a few MB for health-gating in Compose (Chapter 4). The Go image skipped this; Kubernetes won't care either way, because Kubernetes ignores Dockerfile HEALTHCHECKs completely and uses its own probes (Chapter 6). Knowing which layer honors which health mechanism is a classic point of confusion — settle it now.
  • gunicorn with 4 uvicorn workers runs four copies of the FastAPI app in separate processes — Python's way of using multiple CPU cores for one service.

3.3 · frontend-web/Dockerfile — three stages

The Next.js build splits into deps → builder → runner. Why a third stage? So the huge node_modules install (from pnpm install --frozen-lockfile) caches independently: edit a React component and the rebuild reuses the deps layer, re-running only the app build. The runner stage then copies Next.js's standalone output — a self-pruned bundle containing only the modules the app actually imports — which is how a Node app stays under the 200 MB target instead of shipping a 1 GB node_modules.

One subtle line worth understanding: COPY --chown=nextjs:nodejs sets file ownership during the copy. The naive alternative — copy, then RUN chown -R — would duplicate every file into a second layer (layers are diffs; changing ownership rewrites the file in the new layer), roughly doubling that part of the image.

Prove it to yourself

1) EXPOSE 8080 doesn't open a port. So run docker run --rm -p 8080:8080 openrouter/gateway-go:dev after Lab 1 and explain what each side of -p host:container means.
2) Why does the gateway image bake /configs in, when Kubernetes will later mount config from outside? (Hint: what should plain docker run do with no extra setup?)
3) In the backend runtime stage, what would break if the venv had been created at /usr/local in the builder instead of /opt/venv? (Hint: the COPY works because both stages share the same Python at the same path.)

Chapter 4

Docker Compose — many containers, one file

This project isn't one container. Even in development it's Postgres, Redis, NATS, MinIO, Jaeger, Ollama, plus six app services. Starting each with a long docker run command — with the right ports, volumes, environment, and startup order — would be unmanageable. Docker Compose is the answer for a single machine: you declare all services in YAML, and docker compose up creates the containers, a shared private network, and the volumes, in dependency order.

The vocabulary, via this repo's files

Service
One container definition (image, ports, env, volumes). In docker-compose.yml: postgres, redis, nats, minio, jaeger, ollama.
Network & DNS
Compose puts all services on one private network where each service's name is a hostname. That's why the backend's database URL is …@postgres:5432/… and the gateway finds the backend at backend:50051 — no IP addresses, ever. Hold onto this idea: Kubernetes Services (Chapter 6) are the same concept scaled up.
Ports
"5432:5432" publishes container port 5432 onto your host's 5432, so tools on your laptop can reach into the container. Between containers on the compose network, publishing isn't needed at all.
Volumes
Containers are disposable — their writable layer dies with them. A named volume (pgdata:/var/lib/postgresql/data) is Docker-managed storage that outlives containers: destroy and recreate Postgres and your data survives. A bind mount (./backend-python:/app) maps a host folder into the container — this is how the dev setup gets hot reload: you edit a file on your machine, the container sees it instantly.
Healthcheck & depends_on
Every infra service defines a healthcheck (e.g. pg_isready for Postgres). App services declare depends_on: postgres: condition: service_healthy — "don't start me until Postgres answers queries," not merely "until its container exists" (service_started). Started ≠ ready is a distinction that returns with force in Kubernetes.

The two-file overlay pattern

This repo splits Compose across files on purpose — infrastructure in one, app services in another — and merges them at the command line:

shell
docker compose -f docker-compose.yml -f docker-compose.dev.yml up
# or the shortcut:  make up-docker
# see the merged result — the single best way to understand the overlay:
docker compose -f docker-compose.yml -f docker-compose.dev.yml config | less

Later files override/extend earlier ones. Both declare name: openrouter-dev, so they form one project on one network. Why split? You can run just the databases (and run the apps natively via the Procfile) or everything in containers — two documented dev styles in the Makefile. A third file, docker-compose.observability.yml, adds Prometheus + Grafana + Loki + Tempo only when you want them.

The dev overlay has a clever caching design worth studying: instead of building images, it runs upstream bases (golang:1.24-alpine, python:3.12-slim, node:20-alpine), bind-mounts the source for hot reload, and installs dependencies into named volumes (go-mod-cache, py-venv, frontend-node-modules). First boot is slow; every boot after is fast, because the volumes persist. Note the coupling it accepts: backend, worker, and beat share the single py-venv volume so pip installs once — the worker literally busy-waits for /opt/venv/bin/celery to appear.

Landmine

All app services load env_file: .env — and this repo's .env currently contains a real leaked Google OAuth client secret (GOCSPX-…). Rotate it before any push. And note the principle the production images get right: configuration enters at run time via environment, never baked into the image — the same principle Kubernetes implements with ConfigMaps and Secrets.

Landmine

Postgres's official image runs infrastructure/postgres/init.sql (mounted into /docker-entrypoint-initdb.d/) only on first initialization of the data volume. Edit that file later and "nothing happens" — because pgdata already exists. make down-docker-clean (which runs down -v) wipes the volumes and forces re-init.

Chapter 5

Why Kubernetes

Compose is excellent — on one machine. Now imagine this gateway in production, and ask what Compose has no answer for:

  • Traffic needs 50 copies of the gateway across many machines. Which machine runs which copy?
  • A machine dies at 3am. Who notices, and who restarts its containers elsewhere?
  • You deploy a new version. How do you replace 50 running copies without dropping a single request?
  • Traffic spikes 10×. Who adds capacity, and who removes it after?
  • 50 gateway copies exist across machines with changing IPs. How does anything find them?

Kubernetes (K8s) is the industry's answer: an orchestrator that turns a fleet of machines into one logical computer that schedules, heals, scales, and connects containers for you.

The one idea everything rests on: desired state

You do not give Kubernetes commands ("start a container here"). You hand it a YAML document describing the state you want — "three copies of this image, each needing half a CPU, reachable under this name" — and Kubernetes runs a permanent reconciliation loop: measure actual state, compare with desired, fix the difference. A container crashes? Actual (2) ≠ desired (3) → start one. A whole machine dies? Same logic, its pods come back elsewhere. Nobody is paged to restart anything. Every object in Chapter 6 is just a different piece of desired state; every "controller" is just a loop making its piece true.

Cluster anatomy

A Kubernetes cluster

Control plane — API server · scheduler · controllers · etcd (the desired-state database)
Node 1 — kubelet + container runtime → runs pods
Node 2 — kubelet + runtime → pods
Node 3 — kubelet + runtime → pods
kubectl (your terminal) — talks HTTP to the API server
  • Control plane — the brain: the API server (everything talks to it), etcd (stores all the YAML you've applied), the scheduler (decides which node each pod lands on, based on resource requests), and controllers (the reconciliation loops).
  • Nodes — worker machines. Each runs a kubelet agent that starts/stops containers as instructed and reports back.
  • kubectl — the CLI you'll live in. kubectl apply -f file.yaml means "make this desired state so"; kubectl get / describe / logs inspect actual state.
  • minikube — your lab cluster: it runs an entire single-node cluster (control plane + node together) inside a Docker container on this machine. Small, disposable, and API-identical to a 500-node production cluster — which is the whole point: the YAML in this repo doesn't know or care how big the cluster is.

Reading a manifest

Every Kubernetes YAML file ("manifest") has the same four-part skeleton. Learn it once and every file in infrastructure/kubernetes/ becomes readable:

anatomy of any manifest
apiVersion: apps/v1        # which API group/version defines this kind of object
kind: Deployment           # what type of object this is
metadata:                  # its name, namespace, and labels (key:value stickers)
  name: gateway-go
  labels: { app.kubernetes.io/name: gateway-go }
spec:                      # the desired state — the entire point of the file
  …

Labels deserve a sentence: they're arbitrary key:value stickers on objects, and they are how Kubernetes objects find each other. A Deployment manages "pods matching these labels"; a Service routes to "pods matching these labels". No hard links — just label queries (selectors). You'll see app.kubernetes.io/name: gateway-go doing this work all over the repo.

Chapter 6

The Kubernetes objects, via this repo

Kubernetes has dozens of object types; this repo uses about twelve, and they're the twelve that matter. For each: what it is, why it exists, and where this repo uses it.

6.1 · Pod — the atom

A Pod is the smallest deployable unit: one or more containers that share a network identity (one IP, shared localhost) and can share volumes. Usually one container per pod. Crucially: pods are mortal and disposable. They are never healed in place — when one dies, a replacement (new name, new IP) is created. Everything else in Kubernetes is built to make that disposability survivable. You'll almost never write a Pod by hand; you write Deployments that stamp them out.

6.2 · Deployment — "keep N copies running, and upgrade them gracefully"

A Deployment wraps a pod template plus a replica count plus an upgrade strategy. Its controller keeps N pods matching the template alive (self-healing), and when you change the template — a new image version — it performs a rolling update: create some new pods, wait until they're ready, retire old ones, repeat. This repo runs five Deployments: gateway-go, backend-python, backend-celery-worker, backend-celery-beat, frontend-web.

The gateway's rollout config in infrastructure/kubernetes/base/gateway-go/deployment.yaml is the zero-downtime configuration, worth memorizing:

base/gateway-go/deployment.yaml (excerpt)
spec:
  replicas: 3                # desired copies. why 3: survives one node failure + one upgrade surge
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # may temporarily run EXTRA pods during upgrade…
      maxUnavailable: 0      # …but may NEVER kill an old pod before its replacement is Ready

Three sibling details in that file complete the graceful story. When a pod is told to die: (1) it's removed from load-balancing and signaled at the same moment, so a preStop hook of sleep 5 gives the routing layer a head start — no request lands on a dying pod; (2) then SIGTERM, and the process gets terminationGracePeriodSeconds to finish in-flight work before SIGKILL. The three values in this repo tell you exactly what each service does: gateway 30s (drain streaming responses), backend 60s (drain async tasks), celery worker 300s (a video job may run minutes).

Concept · one image, three workloads

backend-python, backend-celery-worker, and backend-celery-beat all run the same image — only the container's command/args differ (remember ENTRYPOINT vs CMD from Chapter 3). They're separate Deployments because they scale on different signals and must fail independently. Beat is pinned to replicas: 1: it's a task scheduler, and two of them would enqueue every periodic job twice.

6.3 · Probes — how Kubernetes knows your app's actual state

Kubernetes can see that a process is running; it cannot know your app is working unless you tell it how to check. That's what probes are — and this is the mechanism that replaces Docker's HEALTHCHECK. There are three, answering three different questions:

ProbeQuestionOn failureGateway values
startuphas it finished booting?keep waiting (other probes paused)/health, up to 30×1s
readinessshould it get traffic right now?remove from load balancing — no restart/ready, every 5s, 3 fails
livenessis it wedged beyond recovery?restart the container/health, every 10s, 3 fails

Why three? Because the failure responses must differ. If the backend briefly loses Redis, the right move is "stop sending it traffic until it recovers" (readiness) — restarting it (liveness) would turn a blip into a rolling outage. The startup probe exists so a slow-booting app (Python: up to 60s here) doesn't need a dangerously lax liveness probe forever. And the celery worker shows the non-HTTP variant: an exec probe that runs celery inspect ping inside the container — the escape hatch for anything that doesn't serve HTTP. In Lab 4 you'll break a readiness probe and a liveness probe separately and watch the two very different outcomes.

6.4 · Resources — requests vs limits

base/gateway-go/deployment.yaml (excerpt)
resources:
  requests: { cpu: 500m, memory: 256Mi }   # 500m = 0.5 CPU cores. RESERVED for scheduling
  limits:
    memory: 512Mi                           # hard cap — exceed it and the pod is OOM-killed
    # note: NO cpu limit — deliberate, see below

Requests are what the scheduler reserves when placing pods on nodes — promises used for bin-packing. Limits are enforcement: exceed a memory limit and the kernel kills the container (OOMKilled — you'll cause one in Lab 6); exceed a CPU limit and the kernel throttles the process. Throttling adds latency spikes, which is precisely why this latency-critical gateway sets no CPU limit while capping memory hard — an opinionated, defensible trade the manifest explains in its own comments. The backend and worker, less latency-sensitive, do carry CPU limits.

6.5 · Service — a stable name for mortal pods

Pods die and return with new IPs, and there are many replicas. A Service gives a set of pods (chosen by label selector) one stable virtual IP and one stable DNS name, load-balancing across whichever pods are currently ready — this is where the readiness probe cashes out. Any pod in the cluster can reach the backend at backend-python:50051; it's Compose's service-name DNS, generalized across machines. The Services here are type ClusterIP (reachable only inside the cluster — correct for internal tiers) with named ports (http, grpc, metrics) so other objects reference the name, not the number.

6.6 · ConfigMap & Secret — configuration lives outside the image

The same image must run in dev, staging, and prod with different settings — so settings can't be baked in. A ConfigMap holds non-sensitive key-values or whole files; a Secret holds sensitive ones (kept separate so access can be restricted and handled more carefully). Pods consume both as environment variables or mounted files. In this repo: the gateway's provider catalogue is a ConfigMap mounted read-only at /etc/gateway/providers.yaml; the Postgres DSN, Redis URL, JWT secret, and Stripe keys arrive via secretKeyRef from Secrets named openrouter-postgres, openrouter-redis, openrouter-app, openrouter-stripe.

Where do those Secrets come from? Not from a file in git — that's the point. base/secrets.yaml declares ExternalSecret objects: instructions for the External Secrets Operator (an add-on) to fetch real values from a Vault server and materialize them as cluster Secrets, refreshing periodically. Secret material never touches the repo; rotation happens in Vault with no redeploy. Elegant in production — and a hurdle for your local cluster, because you have neither the operator nor a Vault. Lab 3 makes solving this the exercise.

6.7 · Namespace — folders inside the cluster

A Namespace partitions one cluster: names are unique per-namespace, and permissions/quotas attach per-namespace. This repo's overlays deploy into openrouter-dev / openrouter-staging / openrouter. Cross-namespace DNS works with a longer name: otel-collector.observability.svc.cluster.local — service otel-collector in namespace observability — which you'll spot in the deployment env vars.

6.8 · Ingress — HTTP(S) from the outside world, routed by hostname

ClusterIP Services are internal. An Ingress is the front door: rules mapping external hostnames/paths to Services, executed by an ingress controller (here: nginx) that a cluster must have installed. base/ingress.yaml maps api.openrouter.example → gateway, app.*/docs.* → frontend, and its annotations are a small masterclass in streaming LLM traffic through nginx:

base/ingress.yaml (excerpt)
nginx.ingress.kubernetes.io/proxy-buffering: "off"     # stream each SSE chunk immediately —
                                                       # buffered, a chat stream would arrive all at once at the end
nginx.ingress.kubernetes.io/proxy-read-timeout: "3600" # an LLM response can stream for minutes;
                                                       # default 60s would cut it mid-sentence
cert-manager.io/cluster-issuer: letsencrypt-prod       # TLS certificates auto-issued & renewed
nginx.ingress.kubernetes.io/limit-rps: "200"           # edge rate-limit before the app's own limiter

Notice the buffering/timeout annotations exist only on the API host, not the dashboard host — real configs have asymmetries like this; templates don't.

6.9 · HPA — automatic scaling

A HorizontalPodAutoscaler continuously adjusts a Deployment's replica count between a floor and ceiling based on metrics. The gateway's (base/gateway-go/hpa.yaml) scales 5→200 pods on three OR-ed signals: a custom requests-per-second metric (target 2000/pod — the leading indicator), CPU 70%, memory 80% (safety nets). Its behavior block encodes the asymmetry every autoscaler should have: scale up fast (up to double, within 30s) because slow reaction drops traffic, scale down slow (max 10%/minute after 5 quiet minutes) because thrashing is worse than briefly over-provisioning. Note also what doesn't have an HPA: the celery worker — queue workers should scale on queue depth, not CPU (a worker at 100% CPU is healthy; a deep queue with idle workers is not), and that needs a different tool (KEDA), a trade-off the Helm values file documents explicitly.

6.10 · PDB, NetworkPolicy, StatefulSet, ServiceAccount — the supporting cast

  • PodDisruptionBudget (pdb.yaml) — caps voluntary disruptions (node maintenance, cluster upgrades): "never evict below N available." It doesn't prevent crashes; it prevents maintenance from causing an outage. Lab 6 shows it physically blocking a node drain.
  • NetworkPolicy — a firewall around pods. By default all pods can talk to all pods; base/gateway-go/networkpolicy.yaml switches the gateway to default-deny with explicit allows: inbound only from nginx and the frontend, outbound only to DNS, the backend, Redis, NATS, telemetry — and to the internet on 443 except 169.254.169.254 (the cloud metadata service) and private IP ranges. That exception list means a compromised gateway pod can reach LLM providers but cannot pivot into the cloud account or internal network. Caveat: policies are enforced by the cluster's network plugin (CNI), and minikube's default doesn't enforce them — they apply and silently do nothing (Lab 6 stretch: start minikube with Calico and watch one actually block).
  • StatefulSet — like a Deployment, but for stateful software: pods get stable names (postgres-0), stable per-pod DNS, and each its own persistent disk that survives rescheduling. Deployment pods are interchangeable cattle; StatefulSet pods are named pets with their own storage. The base runs Postgres (via Patroni, for automatic failover), Redis, and NATS JetStream this way — and Chapter 7 shows prod deleting two of them in favor of managed cloud services.
  • ServiceAccount — a pod's identity for calling the Kubernetes API. These workloads never call it, so every Deployment sets automountServiceAccountToken: false: no credential in the pod means no credential to steal.
  • Security context — every pod here carries the full "restricted" hardening set: runAsNonRoot (with the numeric UID from Chapter 3), all Linux capabilities dropped, no privilege escalation, a default seccomp filter, and readOnlyRootFilesystem: true — the container literally cannot write anywhere except explicitly mounted, size-capped scratch volumes (emptyDir) for /tmp and caches. Making every writable path explicit is the point.

Chapter 7

Environments: kustomize & Helm

Dev wants 1 replica and cheap resources; prod wants 10 and pinned image versions. Copy-pasting the YAML per environment guarantees drift — the copies diverge silently until a prod incident reveals it. Two tools solve this, and this repo ships both, describing the same system — an unusually good side-by-side.

Kustomize: a base plus patches, no templates

Kustomize (built into kubectl) keeps one complete base of plain YAML and layers environment overlays on top — each overlay a small file of differences. kubectl apply -k overlays/dev renders base + patches and applies the result. The base here says, in its own comment, "never apply this base directly" — replica counts, image tags, and hostnames are the overlays' job:

OverlayNamespaceImagesNotable
devopenrouter-dev, names prefixed dev-mutable :dev tagslow replicas, shrunk resources
stagingopenrouter-stagingtagsmid-scale
prodopenrouterimmutable digests, injected by the release pipelinedeletes in-cluster Postgres/Redis via $patch: delete — managed cloud services (from Terraform) replace them

Two mechanisms to understand deeply: the images: transformer rewrites every image reference — dev uses tags for speed, prod pins digests because tags are mutable and digests can't be silently swapped (supply-chain hygiene, straight from Chapter 2). And the configMapGenerator creates ConfigMaps with a content-hash suffix in the name, rewriting all references to match — so changing config produces a "new" ConfigMap name, which changes the pod template, which triggers a rolling restart automatically. That's the answer to the eternal "I changed the ConfigMap, why did/didn't my pods restart?"

Landmine — found while writing this guide

Kustomize rewrites names only in fields it knows about (Service names in Ingress rules, ConfigMap refs in env). It cannot see a name buried in an arbitrary string. The gateway deployment hardcodes GATEWAY_BACKEND_GRPC: backend-python:50051 — but the dev overlay's namePrefix: dev- renames that Service to dev-backend-python. Result: in the dev overlay as written, the gateway cannot resolve its backend. You'll hit and fix this in Lab 3 — a genuine bug found by reading, and a permanent lesson about the limits of name rewriting.

Helm: parameterized templates, for distribution

Helm approaches the problem from the other side: the YAML becomes templates with placeholders ({{ .Values.gateway.replicaCount }}), and per-environment values files fill them in. A packaged template set is a chart; installing one into a cluster creates a release. The ecosystem's rough division of labor: kustomize for environments you own (transparent, plain YAML, easy diffs), Helm for software you hand to strangers — operators who should only touch a values file, flipping switches like gateway.enabled, postgres.embedded, or an air-gapped registry mirror. This repo's chart ships three values files (defaults, values-prod.yaml, values-self-hosted.yaml — the latter turns on in-cluster Ollama for open-weight models) and is honest scaffold: templates exist for the gateway, but backend/frontend/worker templates are not written yet, while values.yaml is complete. Writing the missing templates is Lab 5's deliverable and the best structured Helm exercise this repo offers.

Lab 3 · Deploy to minikube — five failures, five lessons

Goal: the centerpiece. Apply the repo's dev overlay to your cluster, meet five instructive failures, and build a clean local overlay that fixes them. This lab converts Chapters 5–7 into competence.

shell
kubectl kustomize infrastructure/kubernetes/overlays/dev | less   # ALWAYS read rendered output first
kubectl apply -k infrastructure/kubernetes/overlays/dev           # now watch it fail — on purpose
kubectl -n openrouter-dev get pods -w                             # -w = watch live
kubectl -n openrouter-dev describe pod <name>                     # the Events section is your debugger
kubectl -n openrouter-dev logs deploy/dev-gateway-go              # app logs when the container starts at all

The five failures, in the order you'll meet them:

  1. "no matches for kind ExternalSecret / ServiceMonitor / PrometheusRule" — these object types are CRDs (custom types added by operators you haven't installed: External Secrets Operator, Prometheus Operator). Lesson: manifests can depend on cluster add-ons. Fix in your local overlay: exclude those files, and write plain Secret manifests with dev-only values for openrouter-postgres, openrouter-redis, openrouter-nats, openrouter-app, openrouter-stripe.
  2. ErrImagePull / ImagePullBackOff — the cluster wants ghcr.io/openrouter/gateway-go:dev, which exists nowhere; Lab 1 built openrouter/gateway-go:dev in your host's Docker, which minikube's inner Docker can't see. Two fixes — learn both:
    shell
    # option A: retag + load into minikube
docker tag openrouter/gateway-go:dev ghcr.io/openrouter/gateway-go:dev
minikube image load ghcr.io/openrouter/gateway-go:dev     # repeat for backend + frontend
# option B (the classic trick): point your shell at minikube's Docker and build INSIDE it
eval $(minikube docker-env)
make docker && docker tag …                               # builds land directly in the cluster
eval $(minikube docker-env -u)                            # undo when done
  3. CreateContainerConfigError — a pod references a Secret key you didn't create; describe pod names exactly which. This is the eternal error signature of broken secret wiring — learn its face now, cheaply.
  4. Gateway CrashLoopBackOff / can't reach backend — the Chapter 7 landmine: namePrefix: dev- renamed the Service to dev-backend-python, but the hardcoded env var still says backend-python:50051. Fix: in your local overlay drop the prefix, or patch GATEWAY_BACKEND_GRPC. Congratulations — you've debugged a real config bug with describe + logs.
  5. Ingress exists but nothing answers — no ingress controller yet. minikube makes this easy:
    shell
    minikube addons enable ingress                       # installs the nginx controller
kubectl get pods -n ingress-nginx                    # wait Ready
echo "$(minikube ip) api.dev.openrouter.example" | sudo tee -a /etc/hosts
curl http://api.dev.openrouter.example/health
# while iterating, skip DNS entirely:
kubectl -n openrouter-dev port-forward svc/dev-gateway-go 8080:80

Also enable minikube addons enable metrics-server — without it the HPA's CPU metric reads <unknown> (and the custom RPS metric will always read unknown locally; it needs prometheus-adapter — the HPA works fine on CPU/memory regardless, a useful lesson in graceful degradation).

Deliverable: infrastructure/kubernetes/overlays/local/ that applies cleanly to a fresh minikube — the single most instructive thing you can build from this repo. When green: kubectl -n openrouter-dev get deploy,sts,svc,hpa,pdb and a successful curl through the ingress.

Lab 4 · Rollouts, probes, self-healing

Goal: watch the reconciliation loop and probe machinery move — Chapter 6 in motion.

shell
# self-healing: delete a pod, watch its replacement appear in seconds
kubectl -n openrouter-dev delete pod -l app.kubernetes.io/name=gateway-go
kubectl -n openrouter-dev get pods -w

# a zero-downtime rollout, live (surge first, never below capacity — maxUnavailable: 0)
kubectl -n openrouter-dev rollout restart deploy/dev-gateway-go
kubectl -n openrouter-dev rollout status  deploy/dev-gateway-go
kubectl -n openrouter-dev rollout history deploy/dev-gateway-go
kubectl -n openrouter-dev rollout undo    deploy/dev-gateway-go    # one-command rollback

Then break the probes, one at a time: patch the readiness path to /nope — pods go Running but 0/1 Ready, vanish from the Service's endpoints, and are not restarted: traffic-gating, no punishment. Revert, then patch liveness instead — now RESTARTS climbs and eventually CrashLoopBackOff appears. The difference between those two behaviors is the single most important operational concept in Kubernetes; having caused both, you own it.

Goal: read templates the way the cluster does, and complete the scaffold chart.

shell

  -f infrastructure/helm/openrouter/values-self-hosted.yaml | less    # diff mentally vs default render
helm install openrouter infrastructure/helm/openrouter \
  --namespace or-helm --create-namespace --dry-run

Observe: how _helpers.tpl centralizes names/labels; how the gateway.providers block in values becomes the ConfigMap the gateway mounts. Deliverable: write templates/backend/deployment.yaml — mirror the kustomize base's backend deployment, but drive every knob (replicas, image, resources, ports) from values.yaml, which is already fully written. Lab 6 · Failure drills

Goal: meet the classic failure signatures deliberately, where they cost nothing.

  • OOMKill: patch the backend's memory limit down to 128Mi. Find OOMKilled in describe pod and watch CrashLoopBackOff follow (notice: one is the cause, the other the pattern of repeated restarts — people conflate them).
  • PDB vs drain: kubectl cordon minikube then kubectl drain minikube --ignore-daemonsets — watch the PodDisruptionBudget refuse evictions that would drop below its floor. kubectl uncordon minikube to recover.
  • Debugging a scratch container: kubectl exec -it <gateway-pod> -- sh fails — Chapter 3 told you why: there is no shell in scratch. The modern answer: kubectl debug -it <pod> --image=busybox --target=gateway attaches a temporary "ephemeral container" sharing the pod's process namespace — you inspect from beside it, and the tools vanish when you're done.
  • Stretch: minikube delete, then minikube start --driver=docker --cni=calico, redeploy, and prove the gateway NetworkPolicy actually blocks a stray test pod from reaching :8080 — the same policy that silently no-ops on the default network plugin. Security config that isn't tested is decoration; now you know how to test it.

Appendix B

Glossary

Image
A frozen, read-only filesystem + metadata; the shippable unit. Built from a Dockerfile, stored in a registry.
Container
A running instance of an image: an isolated process with a thin writable layer. Disposable by design.
Layer
The filesystem diff produced by one Dockerfile instruction; cached and shared between images.
Registry
A server storing images (Docker Hub, ghcr.io). Tag = mutable version label; digest = immutable content hash.
Volume / bind mount
Storage that outlives containers (named volume) or maps a host folder in (bind mount).
Cluster / node
A set of machines managed as one (cluster); each worker machine (node) runs pods via its kubelet agent.
Pod
Smallest K8s unit: one+ containers sharing an IP. Mortal; replaced, never healed.
Deployment
Keeps N pod replicas running from a template; performs rolling updates; enables rollback.
Service
Stable DNS name + virtual IP load-balancing across ready pods selected by labels.
Ingress
Hostname/path routing rules from the outside world to Services; needs an ingress controller installed.
ConfigMap / Secret
Runtime configuration (plain / sensitive) injected into pods as env vars or files.
Namespace
A named partition of the cluster for grouping, naming, and permissions.
Probe
Startup ("done booting?"), readiness ("traffic now?" → gate), liveness ("wedged?" → restart).
Requests / limits
Scheduler reservation vs hard cap. Memory over limit = OOMKilled; CPU over limit = throttled.
HPA
HorizontalPodAutoscaler — adjusts replica count from metrics between a min and max.
PDB
PodDisruptionBudget — floor on availability during voluntary disruptions (drains, upgrades).
StatefulSet
Deployment-like controller for stateful apps: stable pod names and per-pod persistent disks.
NetworkPolicy
Pod-level firewall rules; enforced only by capable network plugins (CNIs).
CRD / operator
Custom Resource Definition — a new object type added to a cluster, usually with an operator (a controller add-on) that acts on it. E.g. ExternalSecret, ServiceMonitor.
kustomize
Base + overlay patching of plain YAML; built into kubectl (-k).
Helm
Templates + values files packaged as charts; installs create releases.
minikube
A full single-node cluster run locally (here: inside Docker), API-identical to production clusters.
