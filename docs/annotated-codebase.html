1 Foundations

Five ideas you need before any of the code makes sense. If you know all five, jump to Part 2.

1.1 What an API gateway actually is

The problem. You are building an app that uses AI models. OpenAI has an API. Anthropic has a different one. Google has a third. Each has its own URL, its own authentication header, its own request shape, its own response shape, its own billing, its own outages. Supporting three providers means writing and maintaining three integrations. Supporting sixty is a full-time team.

Concept — the gateway / reverse proxy

A proxy is a program that sits between a client and a server and forwards requests. A forward proxy works for the client (your corporate web filter). A reverse proxy works for the server — clients talk to it as if it were the real service, and it decides which machine actually handles the work.

An API gateway is a reverse proxy with opinions. Besides forwarding, it does the things every request needs regardless of destination: check who you are, check you're allowed, count what you used, retry when the far end fails, and translate between formats. Centralizing that means each backend doesn't reimplement it.

This project is an API gateway for LLM providers. It presents one API — OpenAI's, because it's the de facto standard — and translates to whatever the chosen provider actually speaks. The user-visible promise is: change your base_url, keep all your other code, and now you can call any model.

the whole product, in one diff
# Before — locked to one vendor
client = OpenAI(api_key="sk-...")

# After — same SDK, any model on the planet
client = OpenAI(
    api_key="sk-or-v1-...",
    base_url="https://api.openrouter.example.com/api/v1",
)
client.chat.completions.create(
    model="anthropic/claude-sonnet-4-20250514",   # not an OpenAI model!
    messages=[{"role": "user", "content": "hi"}],
)

Everything in this codebase exists to make those six lines work reliably, cheaply, and at high volume. When you're lost in a file, ask: which part of that promise does this serve?

1.2 HTTP, JSON, and what "REST" means here

Concept — HTTP request/response

HTTP is a text protocol. A client opens a TCP connection and sends a request: a method (GET, POST…), a path, some headers (key–value metadata), a blank line, then an optional body. The server replies with a status code (200 ok, 401 unauthorized, 429 too many requests, 503 unavailable), its own headers, and a body.

Headers carry the metadata: Authorization proves who you are, Content-Type says what the body is, X-Request-ID is a custom one this project adds. Status codes are the vocabulary of failure — you'll see this repo choosing them deliberately everywhere.

JSON is the body format throughout — objects, arrays, strings, numbers, booleans, null. Every service here serializes (object → JSON text) on the way out and deserializes (JSON text → object) on the way in. That round trip is where a surprising amount of the code lives, because each provider's JSON has a different shape.

The status codes this project uses on purpose:

1.3 Streaming and Server-Sent Events

The problem. A model generating 800 words takes maybe 20 seconds. If the gateway waits for the whole answer before replying, the user stares at nothing for 20 seconds. Every chat UI you've used shows words appearing as they're generated. That requires the response to arrive in pieces.

Concept — SSE (Server-Sent Events)

Normally the server sends a body of known length and closes. With SSE the server sets Content-Type: text/event-stream and then keeps the connection open, writing small text events as they become available. Each event looks like:

data: {"choices":[{"delta":{"content":"Hello"}}]}
<blank line>
data: {"choices":[{"delta":{"content":" world"}}]}
<blank line>
data: [DONE]
<blank line>

The rules that matter: events are separated by a blank line; fields are name: value lines; the stream ends when the connection closes. SSE is one-directional (server → client) and rides on ordinary HTTP, which is why it beat WebSockets for this use case.

Concept — buffering vs. flushing

Programs don't write to the network one byte at a time; that would be slow. They accumulate output in a buffer and send it when the buffer fills. For streaming that's exactly wrong — your tokens sit in a buffer instead of reaching the user. Flushing forces the buffer out immediately. Every streaming implementation in this repo flushes after each chunk; you'll see http.Flusher in Go doing precisely that.

The hard part

The gateway reads from the provider in fixed-size chunks (32 KB here) — and a chunk boundary can land in the middle of an SSE event, even in the middle of a JSON string. Any code that parses the stream must buffer the leftover partial line and stitch it to the front of the next chunk. Lesson 2.13 walks the state machine that does this correctly.

1.4 Concurrency: processes, threads, goroutines, async

The problem. A gateway handles thousands of requests at once, and nearly all of the time in each request is spent waiting — for Redis, for the provider, for the database. If the program handled one request at a time, it would idle at ~1% CPU while users queued.

Concept — the three models
  • Threads — the OS runs several paths through your program, switching between them. Each thread costs ~1 MB of stack, and switching is relatively expensive. Thousands of threads is a lot; hundreds of thousands is not feasible.
  • Goroutines (Go) — like threads but managed by Go's runtime, starting at ~2 KB and multiplexed onto a small pool of real threads. Hundreds of thousands is normal. You write straight-line blocking code and the runtime handles the switching. This is why the hot path is in Go.
  • async/await (Python, JavaScript) — one thread, one loop. When code hits await, it hands control back to the loop, which runs something else until the awaited thing is ready. Cheap and effective for I/O-bound work — but if any function blocks without awaiting, everything stops.
Where you'll see each in this repo

Go's net/http spawns a goroutine per request automatically — that's why no gateway code says "start a thread." Python is async def / await everywhere, which is also why StripeClient wraps the synchronous Stripe SDK in asyncio.to_thread: calling it directly would freeze the whole event loop. JavaScript on both the server and the browser is the same single-loop model.

Concept — race conditions and mutexes

When two concurrent paths touch the same data, you get a race: the result depends on timing, and it's usually wrong. Classic case — two requests both read "balance = $5", both subtract $3, both write "$2". You spent $6 and were charged $3.

The fixes you'll meet here: a mutex (only one path in the critical section at a time — Go's sync.RWMutex), an atomic operation (indivisible at the hardware level — atomic.Pointer), a database lock (SELECT … FOR UPDATE), a conditional write (UPDATE … WHERE available >= amount), and a server-side script (the Redis Lua rate limiter). Every one of these appears in this codebase, and lesson 7.2 explains why the money code uses two of them together.

1.5 Why three languages, and the line between them

Using several languages in one system is a real cost: three toolchains, three test setups, three sets of idioms for new hires. It's worth it only if the split buys something specific. Here it does, and the boundary is drawn in exactly one place.

RunsLanguageBecause
On every single requestGoCheap concurrency, predictable latency, trivial streaming, one static binary
Occasionally, or in backgroundPythonEvery provider SDK, Stripe, tiktoken, ML libraries, mature migrations
In a browser or terminalTypeScriptIt is the language of both
Concept — the hot path

The hot path is the code that runs on every request, where microseconds multiply by request volume. The warm path runs sometimes. Keeping them in separate services with separate languages lets each be optimized for its own constraint — and lets them scale independently: the gateway scales on requests per second, the backend on database load.

This is why there are auth caches, why there's a gRPC contract, why usage events are published to a queue instead of INSERTed. Every architectural oddity in this repo traces back here.

2.1 cmd/gateway/main.go — starting and stopping a process properly

The problem. A long-running server has to do four things beyond serving traffic: fail immediately if misconfigured, run several listeners at once, reload settings without dropping requests, and shut down without cutting off users mid-response. Getting this wrong shows up as 502s during every deploy.

Concept — the composition root

Somewhere, someone must decide "the auth cache will use this Redis, and this gRPC backend." If that decision is scattered, every file knows about every other file and nothing can be tested alone. The composition root is the single place that does all the wiring, at the outermost edge of the program. Everything inside receives its dependencies as arguments and never constructs them.

gateway-go/cmd/gateway/main.go92 lines
var version = "dev" // injected via -ldflags

func main() {
	if err := run(); err != nil {
		slog.Error("fatal", "err", err)
		os.Exit(1)
	}
}

func run() error {
	// Configuration first — fail fast on bad config.
	cfg, err := config.Load()
	if err != nil {
		return fmt.Errorf("load config: %w", err)
	}

	logger := observability.NewLogger(cfg.Environment, cfg.LogLevel)
	slog.SetDefault(logger)

	shutdownTracer, err := observability.InitTracing(context.Background(), cfg)
	if err != nil {
		return fmt.Errorf("init tracing: %w", err)
	}
	defer shutdownTracer(context.Background())

	srv, err := server.New(cfg, logger)
	if err != nil {
		return fmt.Errorf("build server: %w", err)
	}

	rootCtx, cancel := context.WithCancel(context.Background())
	defer cancel()

	errCh := make(chan error, 2)
	go func() { errCh <- srv.ServeHTTP(rootCtx) }()
	go func() { errCh <- srv.ServeMetrics(rootCtx) }()

	signalCh := make(chan os.Signal, 1)
	signal.Notify(signalCh, syscall.SIGINT, syscall.SIGTERM, syscall.SIGHUP)

	for {
		select {
		case sig := <-signalCh:
			if sig == syscall.SIGHUP {
				logger.Info("SIGHUP received, hot-reloading config")
				if err := srv.ReloadConfig(); err != nil {
					logger.Error("config reload failed", "err", err)
				}
				continue
			}
			cancel()
			shutdownCtx, shutdownCancel := context.WithTimeout(context.Background(), 30*time.Second)
			defer shutdownCancel()
			if err := srv.Shutdown(shutdownCtx); err != nil {
				return err
			}
			return nil
		case err := <-errCh:
			if err != nil && !errors.Is(err, http.ErrServerClosed) {
				return err
			}
		}
	}
}

The walk-through

var version = "dev". Go can overwrite a package variable at link time: go build -ldflags "-X main.version=1.4.2". So the binary knows which build it is without a version file that someone forgets to bump.

main calls run. A small but real idiom. os.Exit skips every defer. If main both deferred cleanup and exited, the cleanup would never run. Splitting them means run can defer freely and return an error, and only main exits.

Concept — defer

defer f() schedules f to run when the surrounding function returns, no matter how — normal return, early return, or panic. It's how Go does "always clean this up," and it's written next to the acquisition so you can see both at once. Here defer shutdownTracer(...) guarantees buffered traces are flushed on any exit path.

fmt.Errorf("load config: %w", err). The %w verb wraps the original error inside a new one that adds context. Callers can still test the inner error with errors.Is / errors.As. You get a readable chain — build server: auth cache: parse url: … — without losing the ability to match on the root cause programmatically. Plain %v would flatten it to a string and destroy that.

Concept — goroutines and channels

go f() runs f concurrently and returns immediately. A channel is a typed pipe between goroutines: ch <- v sends, <-ch receives. An unbuffered channel blocks the sender until someone receives. make(chan error, 2) is buffered with room for two — so both server goroutines can report a failure and exit even if nobody is reading yet. Without the buffer, a goroutine could hang forever trying to report its own death, and leak.

Concept — context.Context

A Context is a value threaded through every function call in a request. It carries a cancellation signal, an optional deadline, and request-scoped values. WithCancel returns a context plus a cancel function; calling cancel() closes the context's Done() channel, and everything watching it stops.

Contexts form a tree: cancel a parent and every child cancels. Here rootCtx is the parent of both listeners, so one cancel() stops the whole server. Inside a request the chain runs the other way — the HTTP request's context is the ancestor of the outbound provider call, so a client hanging up automatically aborts the upstream request instead of wasting money on tokens nobody will read.

select over two channels. select blocks until one of several channel operations is ready, then runs that branch. The loop waits for either a signal or a server failure, whichever happens first.

Three signals, two behaviours. SIGINT (Ctrl-C) and SIGTERM (what Kubernetes sends before killing a pod) mean stop; the code cancels the context, then gives in-flight requests 30 seconds to finish. SIGHUP historically meant "the terminal hung up" and by convention now means "re-read your config" — so it reloads and continues the loop instead of exiting.

!errors.Is(err, http.ErrServerClosed). A deliberately shut-down HTTP server returns this sentinel error. It's not a failure; it's the expected result of asking it to stop. Treating it as fatal would make every clean shutdown log an error.

Why this order

Config → logger → tracing → server. Each step needs the previous one. Config is first because a bad port or a missing Redis URL should kill the process in milliseconds at deploy time, not surface as mysterious 500s an hour later. That's fail fast: crash loudly and early rather than degrade quietly.

2.2 internal/shared/config/ — layered configuration

The problem. The same binary runs on a laptop, in CI, in staging, and in production, each needing different values. Hardcoding is out. One giant env var list is unreadable. And a typo in a setting should be caught at startup, not at 3 a.m.

Concept — configuration layering

Standard practice is to merge several sources in a fixed precedence order, each overriding the last:

  1. Defaults in code — the program runs with zero configuration.
  2. A config file — checked-in, per-environment values.
  3. Environment variables — machine-specific and secret values, highest priority.

Environment variables win because that's what container orchestrators inject, and because secrets must never live in a file in the repo. This is essentially the twelve-factor config rule.

The walk-through

Concept — struct tags

The backtick string after a field — `koanf:"port"` — is a struct tag: metadata attached to the field, ignored by the compiler, readable at runtime through reflection. Libraries use it to map external names to Go fields. You'll see the same mechanism as `json:"model"` in the adapters and `yaml:"base_url"` in the router. One idea, three libraries.

koanf.New("."). The dot is the path delimiter, so config is one flat map with dotted keys: http.port, redis.url. Each loader writes into that map; later loaders overwrite earlier ones. That's the whole precedence mechanism — no special-casing.

The env transform function. Given GATEWAY_HTTP_PORT it strips the prefix, lowercases, and swaps _ for ., yielding http.port. So the nested struct maps to flat env vars by a mechanical rule you can predict without a lookup table.

time.Duration parsed from a string. The default is the string "30s", and the field is a time.Duration (an int64 count of nanoseconds). The unmarshaller converts "30s", "1m", "500ms" automatically. Writing durations as text rather than a bare number removes the classic "is this seconds or milliseconds?" bug.

validate() is where fail-fast lives. Three checks: the port must be a legal TCP port, and the two dependencies the gateway cannot function without must be set. Note what's not checked — it doesn't dial Redis here. Validation is about shape; reachability is the readiness probe's job (lesson 2.14).

Why rawDefaults is a struct with two methods

koanf accepts any type implementing its Provider interface. Rather than a special "defaults" API, the code defines a tiny type with Read() and ReadBytes() and passes it like any other source. That's Go interfaces working as intended: satisfy the method set and you belong, no declaration or inheritance required. The same trick appears in getEnv being a package-level var holding a function — a seam a test can replace.

2.3 internal/api/server/server.go — wiring and routing

The problem. Roughly a dozen components must be constructed in dependency order, handed to each other, and attached to URL paths — with authentication on the paths that need it and not on the health check, or Kubernetes could never verify the pod is alive.

The walk-through

Construction is dependency-ordered. router before proxy, because the proxy needs the router to resolve models and to size its connection pools. Nothing constructs its own dependencies — proxy.New(rt, breakers, logger) receives all three. That's constructor injection, and it's what makes every component testable with fakes.

auth.NewCache(size, ttl, loader1, loader2). The two loaders are variadic — a variable number of trailing arguments. The cache tries them in the order given. Adding a third layer later means passing a third loader here and changing nothing inside the cache. That's the design paying off at the wiring site.

Concept — an HTTP router / mux

A router (or multiplexer) matches an incoming method + path to a handler function. chi adds path parameters (/videos/{job_id}), sub-routers, and middleware that can be scoped to a subtree instead of the whole server. Go's standard library has a simpler one; chi is a thin, idiomatic upgrade that stays compatible with standard http.Handler.

Two middleware scopes, and this is the security-critical bit. r.Use(...) at the top level wraps everything. r.Route("/api/v1", func(r chi.Router){ r.Use(...) }) creates a sub-router whose middleware applies only inside that subtree. So auth and rate limiting protect the API but not /health.

Why health checks must be unauthenticated

Kubernetes probes your pod by making a plain HTTP request. It has no API key. If /health required auth it would always get 401, the pod would be marked unhealthy, and Kubernetes would kill and restart it forever. The distinction between the two endpoints also matters: /health is liveness — "is this process alive?" — and must never check dependencies, because a Redis blip would cause every pod to be restarted, turning a small outage into a total one. /ready is readiness — "should I receive traffic right now?" — and does check dependencies, so an unhealthy pod is quietly removed from the load balancer without being killed.

Timeouts on the http.Server. ReadTimeout bounds how long a client may take to send its request; WriteTimeout bounds the response. Without these, a slow or malicious client can hold connections open indefinitely until you run out of file descriptors — the Slowloris attack. Defaults in Go are no timeout, so setting them is mandatory, not optional.

Defect — WriteTimeout vs. streaming defect

WriteTimeout defaults to 30 s here and applies to the whole response. A long SSE completion that streams for more than 30 seconds will be cut off mid-stream. Servers that stream normally set WriteTimeout: 0 and enforce per-request deadlines through the context instead.

ReloadConfig and the mutex. SIGHUP calls it; it re-parses the provider file and calls s.router.Swap(rt). The sync.RWMutex around it serializes concurrent reloads. The actual swap is atomic — lesson 2.9 explains how in-flight requests keep the old config safely.

2.4 internal/api/middleware/ — the chain

The problem. Every request needs an ID, logging, panic protection, tracing, authentication, and rate limiting. Copying that into forty handlers guarantees someone forgets one — and the one they forget is authentication.

Concept — middleware and Chain of Responsibility

A Go HTTP handler is anything with ServeHTTP(w, r). Middleware is a function that takes a handler and returns a new handler that does something extra and then calls the original. Because the shapes match, they nest arbitrarily:

RequestID(Recoverer(Logger(Tracing(Auth(RateLimit(handler))))))

A request travels inward through each layer and the response travels back outward, so a middleware can act before and after the handler. This is the Chain of Responsibility pattern — and also the Decorator pattern, since each layer wraps without changing the interface.

type ctxKey int

const (
	ctxKeyRequestID ctxKey = iota
	ctxKeyAuth
	ctxKeyStartTime
)

func RequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = uuid.NewString()
		}
		w.Header().Set("X-Request-ID", id)
		ctx := context.WithValue(r.Context(), ctxKeyRequestID, id)
		ctx = context.WithValue(ctx, ctxKeyStartTime, time.Now())
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

func Recoverer(logger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			defer func() {
				if rec := recover(); rec != nil {
					logger.Error("panic recovered", "err", rec,
						"stack", string(debug.Stack()),

				}
			}()
			next.ServeHTTP(w, r)
		})
	}

The walk-through

Two middleware shapes. RequestID is func(http.Handler) http.Handler — it needs no configuration. Recoverer(logger) is a function that returns that shape, closing over the logger. That outer function is a closure factory: it's how you parameterize middleware. Same idea as Python's require_role(*roles) in lesson 3.12.

Concept — context values and why the key type is unexported

context.WithValue(parent, key, val) returns a new context carrying an extra key. Contexts are immutable — you always derive a new one — which is why the code reassigns ctx and passes r.WithContext(ctx) onward.

type ctxKey int with unexported constants is deliberate. If the key were the string "request_id", any other package could use the same string and silently collide. A private type in this package cannot be constructed elsewhere, so collisions are impossible by construction. iota just auto-numbers the constants 0, 1, 2.

RequestID honours an incoming header. If a caller (or an upstream proxy) already set X-Request-ID, it's reused. That's what lets you follow one user action across several services in your logs. Only when absent does it mint a UUID — a 128-bit random identifier collision-free in practice.

Concept — panic and recover

A panic is Go's crash: it unwinds the stack and, if unhandled, kills the whole process. recover() — legal only inside a defer — stops that unwinding and returns the panic value. So Recoverer turns "one bad request crashes the server for everyone" into "one bad request gets a 500."

It's placed second, immediately after RequestID, so it covers every layer beneath it while still having an ID to log. debug.Stack() captures the stack trace for diagnosis — into the log, never into the response, because stack traces tell an attacker your file layout and library versions.

statusRecorder and embedding. Go's ResponseWriter lets you write a status but never read it back, and the logger needs to know what was sent. The fix uses struct embedding: writing http.ResponseWriter with no field name promotes all its methods onto statusRecorder, so it is a valid ResponseWriter for free. Then it overrides only WriteHeader to record the code before delegating. Roughly composition-based inheritance, with one method overridden and everything else forwarded automatically.

Defect — the logger logs an empty key defect

Logger reads AuthIdentityFrom(r.Context()).KeyID, but it is registered before Auth in the chain, so at the moment the log line is written nothing has put an identity into the context. key_id is always "". Middleware order isn't cosmetic — it's data dependency, and here a data dependency runs backwards.

Not calling next.ServeHTTP ends the chain. That's the entire mechanism for rejecting a request — write a response and return. Nothing downstream ever runs. Note that Auth never touches a database and never verifies argon2; it hashes and asks the cache. Lesson 2.5 is that cache.

2.5 internal/repository/auth/ — the three-layer cache

The problem. Every request must answer "is this key valid, and what's it allowed to do?" The truth lives in PostgreSQL, which Go isn't allowed to touch and which would be far too slow anyway. Roughly: an in-process map lookup is ~100 ns, a Redis round-trip ~500 µs, a gRPC call to Python that queries Postgres ~10 ms. That's five orders of magnitude between the cheapest and dearest answer.

Concept — the cache hierarchy

Same principle as CPU L1/L2/L3 cache: put a small fast store in front of a big slow one. Check the fastest first; on a miss, fall through to the next; when you finally get an answer, write it back into every layer you passed so the next request is fast.

This is specifically a read-through cache: callers only ever talk to the cache, and the cache knows how to fetch what it lacks. (Contrast cache-aside, where the caller checks the cache, then the database, then populates the cache itself — lesson 3.19 has one of those.)

Caching always trades freshness for speed. A TTL (time to live) bounds how stale an entry can get. Here it's 60 seconds, which is also how long a revoked key keeps working.

type Loader interface {
	Load(ctx context.Context, keyHash string) (Metadata, error)
}

var ErrCacheMiss = errors.New("auth: cache miss")

type Cache struct {
	ttl     time.Duration
	loaders []Loader

	mu   sync.RWMutex
	data map[string]Metadata // L0 LRU; production swaps for golang-lru/v2
	cap  int

	backend BackendPinger
}

func (c *Cache) Get(ctx context.Context, keyHash string) (Metadata, error) {
	// L0: in-process.
	c.mu.RLock()
	m, ok := c.data[keyHash]
	c.mu.RUnlock()
	if ok && time.Since(m.cachedAt) < c.ttl {
		return m, nil
	}

	// Fall through loaders.
	var lastErr error
	for _, l := range c.loaders {
		m, err := l.Load(ctx, keyHash)
		if err == nil {
			m.cachedAt = time.Now()
			c.put(keyHash, m)
			return m, nil
		}
		if !errors.Is(err, ErrCacheMiss) {
			lastErr = err
			break
		}
		lastErr = err
	}
	if errors.Is(lastErr, ErrCacheMiss) {
		// Cache the negative result briefly to avoid hammering on bad keys.
		neg := Metadata{Valid: false, cachedAt: time.Now()}
		c.put(keyHash, neg)
		return neg, nil
	}
	return Metadata{}, lastErr
}

The walk-through

Concept — interfaces in Go

An interface lists method signatures. Any type with those methods satisfies it implicitly — no implements keyword, no import of the interface. Loader has one method, so redisLoader and backendLoader are interchangeable, and a test can define a three-line fake loader.

Small interfaces are idiomatic Go. A one-method interface is trivially satisfiable and impossible to misuse — compare a five-method interface where a fake must stub four irrelevant methods.

Concept — RWMutex

A plain mutex allows one holder at a time. A read-write mutex distinguishes readers from writers: any number of readers may hold it simultaneously, but a writer excludes everyone. For read-mostly data — which a cache is, overwhelmingly — this removes the bottleneck of serializing reads behind each other.

RLock()/RUnlock() for reading, Lock()/Unlock() for writing. Note the read section is three lines: lock, copy out, unlock. Holding a lock across slow work (a network call!) is the classic way to turn a concurrent server into a serial one.

The TTL check is ok && time.Since(m.cachedAt) < c.ttl. Present in the map isn't enough; it must also be fresh. Expired entries simply fall through to the loaders and get overwritten. There's no background eviction sweep — expiry is checked lazily on read, which is simpler and costs nothing when nobody asks.

The loader loop distinguishes two error kinds. A ErrCacheMiss means "I don't have it, ask the next one" → keep looping. Any other error means the layer is broken → break immediately and report. Falling through on a real error would mask an outage as a missing key and return 401 to every legitimate user — far worse than an honest 503.

Concept — sentinel errors and errors.Is

A sentinel error is a package-level error value used as a signal — ErrCacheMiss here, io.EOF and http.ErrServerClosed in the standard library. Because errors get wrapped with %w as they travel up, you compare with errors.Is(err, Target) rather than ==: it unwraps the whole chain looking for a match.

Negative caching. When every layer reports a miss, the cache stores {Valid: false} anyway. Without this, an attacker firing random keys would send every single request through Redis, gRPC, and Postgres — a trivially cheap way to overload your database. With it, each bad key costs one expensive lookup per TTL window.

Defect — this is not an LRU defect

The eviction in put() is:

if len(c.data) >= c.cap {
	for ek := range c.data { delete(c.data, ek); break }
}

Go randomizes map iteration order, so this deletes an arbitrary entry — quite possibly your hottest key. A real LRU (least-recently-used) evicts the entry untouched for longest, which requires tracking access order in a linked list. The comment in the file acknowledges this and names the fix: hashicorp/golang-lru/v2. Under memory pressure the current code degrades your hit rate for no reason.

2.6 internal/repository/auth/grpc_client.go — talking to Python

Concept — gRPC and Protocol Buffers

REST sends human-readable JSON over HTTP/1.1 with meaning encoded in URLs and verbs. gRPC instead lets you call a function on another machine as if it were local. You write a .proto file describing messages and services, run a code generator, and get client and server classes in every language you need.

Protocol Buffers is the encoding: binary, schema-driven, much smaller and faster to parse than JSON. Fields carry numeric tags rather than names, which is what makes evolution safe — add a field with a new tag and old code ignores it; never reuse a tag.

gRPC rides on HTTP/2, so many calls multiplex over one connection with no head-of-line blocking. For internal service-to-service traffic that's a clear win: type safety from the shared schema, and no hand-written JSON parsing on either side.

	// negative-cache TTL uniformly with Redis misses.

Concept — sync.Once and lazy initialization

once.Do(f) runs f exactly once, ever, no matter how many goroutines call it simultaneously; the rest block until the first finishes. It's the safe way to do lazy one-time setup under concurrency.

Why lazy? If the gateway dialled the backend during startup and the backend were down, the gateway would fail to start — and since almost every request is served from cache, it doesn't actually need the backend to be useful. Deferring the connection means a backend outage degrades the gateway instead of preventing it from booting.

The err field is remembered too. If the first attempt fails, c.err is set and every later call returns the same error without retrying. That's a deliberate simplification with a real cost: a backend that was down at first contact stays permanently unreachable to this client until the process restarts. A production version would need a reconnect path.

The unknown_key translation. Python answers "no such key" as a valid response with valid=false. The client converts it into ErrCacheMiss so the layer above treats a Postgres miss identically to a Redis miss — and applies negative caching to both. Without this, unknown keys would return {Valid:false} as a successful load, which happens to work here, but the explicit translation keeps one meaning per error value.

Security note — insecure.NewCredentials()

That's unencrypted, unauthenticated plaintext gRPC. The comment says mTLS comes from a service mesh in production. That may be a fine architecture — but no mesh manifest exists in this repo, so as shipped, API-key metadata and budgets cross the network in the clear. Trusting infrastructure you haven't deployed is how "secure by design" becomes "insecure in fact."

2.7 internal/service/ratelimit/ — a sliding window in Lua

The problem. Each key may make N requests per minute. The counter must be shared across every gateway pod (so five pods don't grant 5N), must be correct under concurrency, and must cost well under a millisecond.

Concept — fixed vs. sliding window

A fixed window counts per clock minute and resets at :00. It's trivial and has a nasty edge: a client can send N requests at 10:00:59 and N more at 10:01:00 — 2N in one second, all "within limits."

A sliding window asks "how many in the last 60 seconds from right now?" No boundary to exploit. It costs more because you must remember individual request timestamps rather than a single integer.

Concept — Redis sorted sets, and why Lua

A Redis sorted set holds members each with a numeric score, kept ordered. Score the members by timestamp and you can delete everything older than a cutoff in one command and count what remains in another.

But that's three commands — trim, count, add — and between them another pod could act. Redis executes a Lua script atomically: the whole script runs start to finish with nothing interleaved. That turns read-modify-write into one indivisible operation, which is exactly what a correct limiter needs.

gateway-go/internal/service/ratelimit/limiter.go109 lines · trimmed
const slidingWindowScript = `
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit  = tonumber(ARGV[2])
local now    = tonumber(ARGV[3])
local member = ARGV[4]

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
local count = redis.call('ZCARD', key)
if count < limit then
  redis.call('ZADD', key, now, member)
  redis.call('PEXPIRE', key, window)
  return {1, limit - count - 1, now + window}
end
return {0, 0, now + window}
`

func (l *redisLimiter) Check(ctx context.Context, k Key) (Result, error) {
	if k.RequestsPerMinute == 0 {
		return Result{Allowed: true, …}, nil   // no policy => unlimited
	}
	now := time.Now()
	resp, err := l.client.Eval(ctx, slidingWindowScript,
		[]string{"rl:" + k.KeyID},
		60_000, k.RequestsPerMinute, now.UnixMilli(),
		fmt.Sprintf("%d", now.UnixNano()),
	).Result()
	…
}

The script, line by line

  1. ZREMRANGEBYSCORE key 0 (now-window) — delete every entry older than 60 s. The window "slides" simply by moving the cutoff.
  2. ZCARD key — count what survived: requests in the last 60 s.
  3. If under the limit: ZADD records this request at score now, and PEXPIRE sets a 60 s TTL on the whole key so idle users' data evaporates instead of accumulating forever.
  4. Return a triple: allowed flag, remaining quota, reset timestamp. Lua returns arrays as Redis multi-bulk replies, which Go receives as []interface{}.

The member must be unique. It's now.UnixNano(). A sorted set is a set — adding a duplicate member updates its score instead of adding a row, so two requests in the same millisecond would count as one. Nanosecond precision makes collisions effectively impossible.

RequestsPerMinute == 0 means unlimited, checked before touching Redis. Internal or admin keys skip the network hop entirely.

Why the test fails, and why it isn't a bug test-only

TestLimiter_ResetAtIsInTheFuture fails. The tests use miniredis, an in-process Redis fake, whose embedded Lua clamps large integers to 32 bits — so now + window (about 1.79 × 10¹²) comes back as -2147483648, a date in 1969. Real Redis returns 64-bit integers and behaves correctly. This is a limitation of the test double, not of the code. It's still worth fixing, because a permanently red test trains everyone to ignore the test suite.

2.8 internal/repository/cache/exact.go — the response cache

The problem. Provider calls cost money and take seconds. If two users send byte-identical requests, the second can be served from memory for free.

Concept — hashing as a cache key

A hash function maps input of any size to a fixed-size digest, deterministically: same input, same digest, always. SHA-256 produces 256 bits and is cryptographic — infeasible to find two inputs with the same digest.

Using a hash as the cache key means "same request" becomes a fast fixed-length comparison instead of comparing potentially megabytes of JSON.

What's not in the key

No org ID, no user ID. Two different customers sending identical requests share a cached response. That's defensible — the response is a pure function of the request, so nothing private leaks — but it's an isolation decision that deserves to be documented rather than implicit, and some compliance regimes will not accept it.

Defect — the cache is never written defect

Concept — atomic pointer swap (copy-on-write)

The naive approach is a mutex around the config map: every reader locks, every reload takes the write lock. Correct, but readers now contend on a lock on the hottest path in the program.

The better approach: never mutate the config. On reload, build a completely new one, then swap a single pointer. A pointer swap is atomic — the hardware guarantees no reader ever sees a half-written pointer. Readers do one unsynchronized load with no lock at all.

Requests already running keep the old snapshot until they finish, then future requests see the new one. Nothing is freed while in use because Go's garbage collector won't collect the old state until the last reader drops it. Elegant, and it only works because the data is treated as immutable.

Concept — the Strategy pattern

When several algorithms solve the same problem differently and the choice is made at runtime, define one interface and one implementation per algorithm. Callers depend on the interface and never branch on which one they got. Adding "route by carbon intensity" means adding a file, not editing a switch — which is the Open/Closed Principle in practice.

copy before sorting. Sorting in Go mutates in place. Sorting the caller's slice would be a surprising side effect on shared data. Copying first keeps Order a pure function.

SliceStable, not Slice. A stable sort preserves the relative order of items that compare equal. With three providers at identical prices, stability keeps the YAML's ordering as the tiebreak — deterministic and explainable, instead of results that shuffle between deploys.

PricingLookup is an interface, not a map. The strategy declares what it needs — "tell me a cost" — without saying where it comes from. Production reads Redis; a test passes a literal. That's dependency inversion: the policy defines the interface, and the mechanism conforms to it.

2.10 internal/service/circuitbreaker/ — failing fast

The problem. A provider goes down. Every request now waits 120 seconds for a timeout, then fails. Those requests occupy memory and connections while waiting, so the queue grows until the gateway itself falls over. One dependency's outage becomes your outage — a cascading failure.

Concept — the circuit breaker

Named after the electrical device: when current is dangerous, it opens and stops the flow.

  • Closed — normal. Requests pass; failures are counted.
  • Open — too many failures. Requests are rejected instantly, without touching the dead provider. No waiting, no resource consumption.
  • Half-open — after a cooldown, let a few probes through. If they succeed, close and resume. If they fail, open again.

The half-open state is the clever bit: it's how the system recovers automatically without a human, while limiting the recovery attempt to a handful of requests rather than the full flood.

			Interval:    60 * time.Second, // counters reset
			Timeout:     30 * time.Second, // open → half-open
			ReadyToTrip: func(c gobreaker.Counts) bool {
				return c.ConsecutiveFailures >= 5
			},
		},
	}
}

func (r *Registry) For(provider, model string) *gobreaker.CircuitBreaker {
	key := provider + ":" + model
	r.mu.RLock()
	cb, ok := r.breakers[key]
	r.mu.RUnlock()
	if ok { return cb }

	r.mu.Lock()
	defer r.mu.Unlock()
	// Double-check after acquiring write lock.
	if cb, ok := r.breakers[key]; ok { return cb }
	settings := r.settings
	settings.Name = key
	cb = gobreaker.NewCircuitBreaker(settings)
	r.breakers[key] = cb
	return cb
}
Concept — double-checked locking

Reading is common; creating is rare. So: take the cheap read lock and look. If found, done. If not, take the write lock — and look again. The second check matters because between releasing the read lock and taking the write lock, another goroutine may have created it. Without the re-check you'd construct two breakers for the same provider, and each would see only half the failures. The pattern is standard for lazy initialization of a shared map.

One breaker per (provider, model), not per provider. If gpt-4o is degraded but gpt-4o-mini is healthy, a provider-level breaker would cut off both. Finer granularity isolates the actual failure. The trade-off is slower detection — failures are spread across more counters — and unbounded map growth if model IDs are attacker-controlled.

ConsecutiveFailures >= 5. Consecutive means one success resets the count to zero. That tolerates intermittent errors, which is usually what you want, but it means a provider failing 50% of requests may never trip. An error-rate policy would; gobreaker supports that via the same ReadyToTrip function, which receives the full counts.

Interval: 60s vs Timeout: 30s. Easy to confuse. Interval is how often counters reset while closed. Timeout is how long the breaker stays open before trying half-open. Different clocks, different jobs.

The rule: once one byte is written, you can no longer fail over. The loop must track whether the response has been committed and, if so, abort rather than retry.

Concept — connection pooling

Opening an HTTPS connection costs a TCP handshake plus a TLS handshake — easily 100 ms across the internet. Doing that per request would dominate your latency. A pool keeps connections open and reuses them, so most requests skip both handshakes.

MaxIdleConnsPerHost is the setting people miss: Go's default is 2. Under load, connections beyond the second are closed and reopened constantly, and throughput collapses. Setting it to 50 here is one of the highest-value lines in the file.

Concept — sync.Pool

Allocating a 32 KB buffer per streaming request means the garbage collector has to reclaim thousands of them per second. sync.Pool keeps used objects for reuse — Get returns a spare or calls New; Put hands one back. It's specifically designed for short-lived, interchangeable temporary objects on a hot path.

Defect — the pool allocates on every Put defect

putBuffer(b []byte) does bufPool.Put(&b). b is a local parameter; taking its address forces it to escape to the heap, so every call allocates a fresh slice header. You avoid allocating the 32 KB array and then allocate a header instead — the pool works, but leaks a small allocation per request that it exists to prevent. The idiomatic form passes *[]byte throughout, so no address is ever taken of a local.

Security — Proxy: http.ProxyFromEnvironment

This honours HTTP_PROXY/HTTPS_PROXY from the environment. Anyone who can set an env var on the pod can route every provider call — API keys included — through a machine they control. Production should pin Proxy: nil.

type anthropicStreamTranslator struct {
	lineBuf      bytes.Buffer // partial line carryover across Translate calls
	currentEvent string       // most recent `event:` value
	currentData  bytes.Buffer // accumulated `data:` payload

	id      string   // populated from message_start
	model   string
	created int64

	roleEmitted bool
	finished    bool
}

func (t *anthropicStreamTranslator) Translate(chunk []byte, w io.Writer) error {
	t.lineBuf.Write(chunk)
	for {
		raw := t.lineBuf.Bytes()
		nl := bytes.IndexByte(raw, '\n')
		if nl < 0 { break }          // incomplete line — wait for more bytes
		line := raw[:nl]
		t.lineBuf.Next(nl + 1)       // consume it
		if len(line) > 0 && line[len(line)-1] == '\r' {
			line = line[:len(line)-1]
		}
		if len(line) == 0 {          // blank line = event boundary
			if err := t.dispatch(w); err != nil { return err }
			t.currentEvent = ""
			t.currentData.Reset()
			continue
		}
		t.consumeLine(line)
	}
	return nil
}

The walk-through

Concept — a streaming parser

When data arrives in arbitrary pieces, you cannot parse in one pass. The standard shape is: append new bytes to a buffer, consume every complete unit you can find, leave the remainder in the buffer, return, and repeat on the next chunk. State that must survive between calls lives in the struct — here the partial line, the current event name, and the accumulating data payload.

  1. Append. t.lineBuf.Write(chunk) adds the new bytes to whatever was left over.
  2. Find a newline. No newline means no complete line: break and wait for the next chunk. This single check is what makes split events safe.
  3. Consume it. t.lineBuf.Next(nl+1) advances past the line and its newline, so the buffer holds only unprocessed bytes.
  4. Strip \r. Line endings may be \r\n or \n. Failing to strip it would leave a stray carriage return inside the parsed JSON.
  5. Blank line = event complete. This is the SSE framing rule. Dispatch the accumulated event, then reset for the next.
  6. Otherwise it's a field line — event: or data: — handled by consumeLine, which appends to the buffers. Multiple data: lines for one event are joined with a newline, per spec. Comment lines starting : are ignored.

dispatch is the translation table. message_start captures the ID and model and emits the opening delta:{role:"assistant"} chunk that OpenAI clients expect first. content_block_delta becomes delta.content — but only when Delta.Type == "text_delta", so tool-call deltas are dropped rather than mangled. message_delta carries the stop reason and becomes finish_reason. Events with no OpenAI equivalent — ping, content_block_start, message_stop — return nil and vanish.

Close writes data: [DONE] and is idempotent via the finished flag. Idempotence matters because the caller may invoke it on both a normal EOF and an error path; emitting [DONE] twice would confuse clients.

finish_reason is *string, a pointer. The OpenAI schema requires the field present on every chunk, as null until the last one. A plain string with omitempty would omit the key entirely; without omitempty it would send "". Only a pointer serializes as JSON null. A small detail that determines whether real SDKs parse your stream.

Why the passthrough translator is fine

OpenAI-compatible providers already emit the right format, so their translator copies bytes verbatim without parsing — including across split events. That's safe: HTTP is a byte stream and the client reassembles. You only need a parser when you must understand the content, which is precisely when the provider's format differs.

Nineteen lessons covering backend-python/. Where Go is one flat service optimized for speed, this is a layered application optimized for change — so we start with the layering, then work outward from the domain.

Concept — layered n-tier architecture

The idea is a rule about which direction imports may point. Three tiers, imports pointing downward only:

api  →  service  →  repository        (any tier may import shared)
             ↑
   service/domain declares Port interfaces; repository implements them

api holds delivery — routes, dependency wiring, error translation.
service holds use cases — "issue a key," "meter usage" — and service/domain holds the business concepts they orchestrate: what an API key is, what money is, and the Port interfaces. It imports no framework at all.
repository holds mechanisms — SQLAlchemy, Redis, Stripe, HTTP clients — implementing the Ports the service tier declares.
shared holds cross-cutting utilities — config, logging, tracing, security.

The payoff: swapping PostgreSQL for something else touches the repository tier only. Business rules can be unit-tested with no database, no network, and no fixtures. The cost is more files and a layer of indirection, which is only worth paying on a system expected to live for years.

Concept — dependency inversion

How can the inner ring use a database it isn't allowed to import? It declares an interface — "something that can find a key by hash" — and infrastructure writes a class satisfying it. The inner ring depends on its own abstraction; the outer ring depends on that abstraction too. Both point inward. That inversion is the whole trick, and every ABC in domain/repositories.py is an instance of it.

3.4 app/shared/security.py — the two-hash scheme

The most important security design in the project, and the reason to read this lesson twice.

Concept — why you never store a secret directly

Databases leak. If yours contains API keys in plaintext, every customer is compromised the moment it does. So you store a hash — a one-way digest. To check a presented key you hash it and compare digests; you can verify without ever holding the original.

Concept — why SHA-256 alone is not enough

SHA-256 is fast — deliberately, since it's built for integrity checking. Modern hardware computes billions per second, so an attacker with your database can brute-force weak secrets at enormous rates.

argon2id is designed for the opposite goal. It's deliberately slow and, crucially, memory-hard: each hash requires a large block of RAM (64 MB here). GPUs get their advantage from thousands of tiny cores with little memory each, so a memory requirement removes the attacker's parallelism. It also salts automatically, so identical inputs produce different digests and precomputed rainbow tables are useless.

Concept — the conflict, and the resolution

Here's the bind. You want argon2 for at-rest safety. But argon2 takes ~100 ms and 64 MB — you cannot afford it per request. Worse, you can't even look up the row by argon2 hash, because the salt differs every time: the same key hashes differently on every computation, so it can't be an index.

The resolution is to store two hashes of the same secret, each doing one job:

  • key_lookup — SHA-256, deterministic, unique, indexed. Its job is to find the row, in one index seek.
  • key_hash — argon2id, salted, slow. Its job is to be useless to a thief.

Validation is: SHA-256 the presented key → index seek → one argon2 verify on the single candidate. You get a memory-hard hash without paying for it on lookup. And since Go caches the result for 60 seconds, the overwhelming majority of requests pay for neither.

Concept — secrets vs random

Python's random is a Mersenne Twister: fast, reproducible, and predictable — observe enough output and you can compute the internal state and every future value. Fine for simulations, catastrophic for tokens. secrets draws from the OS cryptographic random source. token_hex(32) gives 32 bytes = 256 bits of entropy, which is unguessable by any physical means.

The sk-or-v1- prefix. Human-readable provenance, and a version marker so the format can change later. It also makes keys detectable by automated secret-scanners — GitHub can spot a leaked key by its prefix, which is a real operational win.

Concept — entities vs. value objects

A value object is defined entirely by its values: $5 is $5, and there's no meaningful "which $5." Compare by value, and make it immutable — because if you could mutate the $5 in someone's wallet, everyone holding a reference to it would be affected.

Concept — frozen=True and slots=True

frozen=True makes assignment after construction raise, and generates __hash__ so instances can be dict keys and set members. slots=True replaces the per-instance __dict__ with a fixed layout — less memory, faster attribute access, and no accidental new attributes.

Concept — never use float for money

float is binary floating point. It cannot represent 0.1 exactly, so 0.1 + 0.2 == 0.30000000000000004. Accumulate that over a million billing rows and your ledger drifts.

Decimal is base-10 with exact arithmetic. Note Decimal("1000000") is constructed from a string — Decimal(0.1) would inherit the float's error before Decimal ever saw it. Same discipline appears in the database as NUMERIC(14,6) rather than DOUBLE PRECISION.

Invariants live in the constructor. __post_init__ runs after the generated __init__, and raising there means a negative Money cannot exist anywhere in the program. This is making illegal states unrepresentable: once constructed, an object is valid, so no downstream code needs to re-check.

Operator overloading with a guard. __sub__ lets you write a - b, and it refuses to produce a negative. Subtracting more than you have is a bug that surfaces at the moment it happens rather than as a mysterious negative balance three layers later.

3.10 Unit of Work

Concept — transactions and atomicity

A transaction groups statements so they all take effect or none do. Creating a user, their organization, and their first key is three INSERTs; if the third fails, you must not be left with an orphaned user. COMMIT makes it permanent, ROLLBACK discards it.

The catch: each repository holds its own connection by default, so they'd be in different transactions and partial failure becomes possible again.

Concept — the Unit of Work pattern

One object owns the transaction and hands the same session to every repository. Enter it, use any repositories you like, commit once. Exit without committing — or by raising — and everything rolls back. The transaction boundary becomes a visible async with block instead of an invisible convention.

        self.video_jobs    = SqlVideoJobRepository(self._session)

        try:

        finally:

    async def commit(self) -> None:
        await self._session.commit()
Concept — the async context manager protocol

async with obj: calls await obj.__aenter__() and binds the result; on leaving the block it calls await obj.__aexit__(exc_type, exc_val, tb). Those three arguments are None on a clean exit and describe the exception otherwise — which is exactly how the code knows whether to roll back.

The finally is the important detail: close() runs on every path, so the connection returns to the pool even if the rollback itself explodes. Leaked connections exhaust the pool and hang the whole service.

Repositories are constructed inside __aenter__. They don't exist before the session does, so it's impossible to hold a repository with a stale or closed session. Late binding used as a safety property.

Commit is explicit; rollback is automatic. The asymmetry is deliberate — forgetting to commit loses work, which you notice immediately in a test; forgetting to roll back corrupts data, which you notice much later.

CreatedKey exists purely to carry it out of this one function; every later read of the key returns the entity without it. This is the "we can't recover your key, generate a new one" behaviour you've met on every API platform.

validate_for_request is the two-hash scheme in four lines. SHA-256 → index seek → argon2 verify → business invariants. Reading it top to bottom is the clearest statement of lesson 3.4 in the codebase.

Subtle — verify even after the lookup matched

Finding a row by key_lookup already proves the SHA-256 matched. Why verify argon2 too? Because if an attacker ever gets write access to the lookup column, or a collision is somehow engineered, the argon2 check is an independent second gate. Defence in depth: the cheap check finds the row, the strong check authorizes.

BillingService.meter follows the same shape: a command in, cost computed by the value object, deduct_atomic called, a UsageRecord appended, one commit. Note cost = ... if not cmd.cache_hit else Money.zero() — cache hits are free, and that rule lives in exactly one place.

OAuthService.exchange is the most involved: call the provider's userinfo endpoint over httpx, find-or-create a User and Organization, and mint a backend JWT. Concept — decorators and functools.wraps

A decorator is a function that takes a function and returns a replacement. @audit_log(...) is a decorator factory — it's called with arguments and returns the actual decorator, hence three nested levels.

functools.wraps copies the original's name, docstring, and — the part that matters here — a __wrapped__ reference. FastAPI inspects handler signatures to work out what to inject; inspect.signature follows __wrapped__, so dependency injection still works through the wrappers. Omit wraps and FastAPI sees (*args, **kwargs), injects nothing, and every route breaks.

require_permission fails closed. If it can't find an AuthContext among the injected kwargs — a misconfigured route — it denies. The alternative, allowing when unsure, turns a wiring mistake into an authorization bypass.

audit_log runs after success and swallows its own failures. Both choices are deliberate: recording an action that then failed would produce a false audit trail, and a full audit table shouldn't take your API down. def filter(self, *, needs_tools=False, needs_vision=False, needs_streaming=False,
           user_geo="", data_residency=()) -> list[Candidate]:
    required: set[str] = set()
    if needs_tools:     required.add("tools")
    if needs_vision:    required.add("vision")
    if needs_streaming: required.add("streaming")

    survivors = []
    for entry in self.pool:
        if not required.issubset(entry.capabilities):                       continue
        if user_geo and "*" not in entry.geos_allowed and user_geo not in entry.geos_allowed: continue
        if data_residency and not set(data_residency).intersection(entry.residency):          continue
        if entry.quality_score < self.quality_floor:                        continue
        if entry.latency_p50_ms > self.latency_max_ms:                      continue
        survivors.append(entry)
    return [e.to_candidate() for e in survivors]
Concept — filter, then rank

Two distinct stages. Filtering removes candidates that cannot serve the request — no vision support, wrong jurisdiction, below the quality floor. These are hard constraints; no amount of cheapness compensates. Ranking then orders whatever survived by a preference. Collapsing the two into one score is a common mistake: it lets a very cheap model outrank a legal requirement.

Set operations express the rules exactly. required.issubset(entry.capabilities) is "has everything we need." set(a).intersection(b) is "overlaps at least one jurisdiction." Both read as the business rule they encode, and both are O(1)-ish rather than nested loops.

Keyword-only arguments. The bare * in the signature forces every caller to name its arguments. filter(True, False, True) would be unreadable and easy to get wrong; filter(needs_tools=True, needs_vision=False) cannot be misordered.

Concept — a three-outcome chain

Most Chain-of-Responsibility examples have two outcomes: pass or stop. This one has three — pass, block (short-circuit immediately), and redact (rewrite the text and keep going). They make the interface real and testable today. The pipeline has unit tests because it has something to run. When the ML models arrive, they slot in behind the same Guardrail.check() signature and nothing else changes. The alternative — waiting for the real implementation before defining the interface — is how you discover at integration time that your abstraction was wrong.

The requirement is that the stub is labelled. A regex called "PII detection" that nobody documented as a placeholder will eventually be trusted in a compliance review.

Concept — two queues, two guarantees

This project uses both NATS and Celery, which looks redundant until you see what each guarantees.

NATS JetStream — publish/subscribe for high-volume telemetry. Fast, and losing an occasional usage event during an incident is survivable. Publishers don't know or care who subscribes.

Celery — a durable task queue for work that must not be lost: charging a card, generating a video, delivering a webhook. Tasks are persisted, retried with backoff, and acknowledged only on completion.

Using one for both means either paying durability costs on telemetry, or risking losing a payment. Different guarantees, different tools.

Retrying a failed call immediately usually fails again and adds load to something already struggling. Exponential backoff waits 1 s, 2 s, 4 s, 8 s… giving the far end room to recover.

The receiver needs to know the webhook really came from you. HMAC combines the message with a shared secret to produce a tag that can't be forged without the secret. The receiver recomputes it over the received bytes and compares.

The same buffering discipline as the SSE translator in lesson 2.13 — whenever producer and consumer disagree about chunk sizes, this is the shape of the answer.

Signed URLs. generate_signed_url produces a time-limited URL that grants access to one private object without credentials — 24 hours here. It's how you serve generated media directly from object storage without proxying bytes through your API or making the bucket public.

4 The frontend

Next.js 15, React 19, Tailwind 4. The interesting parts aren't the components — they're where code runs (server vs. browser) and how a secret gets to the API without passing through the user's JavaScript.

4.1 Server Components — where does this code run?

Concept — the three rendering models

Server-side rendering (SSR), classic. The server builds HTML, sends it, then the browser downloads the same components again as JavaScript and re-attaches event handlers — hydration. Fast first paint, but you shipped every component twice.

Single-page app (SPA). Send an empty page plus a large JS bundle; the browser renders everything. Slow first paint, poor SEO, but rich interaction.

React Server Components (RSC). Components are marked server or client. Server components run only on the server, can await a database call directly, and ship zero JavaScript to the browser — their output is serialized UI, not code. Only components needing interactivity become client components.

The practical effect: a dashboard that's mostly text and tables ships almost no JavaScript.

the boundary rule
// Server Component — the default. No directive needed.

// Client Component — opt in explicitly.

Concept — streaming with <Suspense>

The dashboard wraps each card in <Suspense fallback={<Skeleton />}>. The server sends the page shell immediately with skeletons in place, then streams each card's real HTML as its data arrives. One slow query delays one card instead of the whole page. This works because the connection stays open and the server keeps writing — the same underlying mechanism as SSE in lesson 1.3.

Layered n-tier organizes the tree by tier rather than by file type: app/ (routes — the App Router filesystem, outside the tiers) → api/ (presentation: components by area, layout blocks, ui primitives) → service/ (business: env config, hooks, providers, UI domain types) → repository/ (data: the API client and per-entity fetchers) → shared/ (cross-cutting utilities). Imports may only point downward. The benefit over a flat components/ folder is that responsibilities have one home each — a data-fetching change touches repository/, not five component folders.

4.3 The BFF proxy

The problem. The browser needs to call the gateway with a bearer token. Putting the token in client JavaScript exposes it to any XSS bug, any browser extension, and anyone who opens devtools.

Concept — Backend for Frontend

Put a thin server layer between the browser and the real API. The browser authenticates to it with an httpOnly cookie — a cookie JavaScript cannot read, so XSS can't steal it. The BFF exchanges that cookie for the real token server-side and forwards the call. The token never enters the browser at all.

Bonus: requests are same-origin, so no CORS preflight and no cross-site cookie complications.

frontend-web/src/app/api/proxy/[...path]/route.tstrimmed
async function proxy(req: NextRequest, { params }: RouteParams) {
  const session = await auth();
  const accessToken = (session as { accessToken?: string } | null)?.accessToken;
  if (!accessToken) {
    return NextResponse.json({ error: { message: "Not authenticated", … } }, { status: 401 });
  }

  const { path } = await params;
  const target = new URL(`${serverEnv.NEXT_PUBLIC_API_BASE_URL}/api/v1/${path.join("/")}`);
  for (const [k, v] of req.nextUrl.searchParams) target.searchParams.set(k, v);

  const upstream = await fetch(target, {
    method: req.method,
    headers: filterHeaders(req.headers, accessToken),
    body: req.method === "GET" || req.method === "HEAD" ? undefined : await req.arrayBuffer(),
    redirect: "manual",
  });

  // Stream SSE responses through unchanged so playground streaming works.
  return new NextResponse(upstream.body, {
    status: upstream.status,
    headers: passthroughHeaders(upstream.headers),
  });
}
export const GET = proxy; export const POST = proxy; …

[...path] is a catch-all route. Everything under /api/proxy/ lands here with the segments as an array. One file proxies the entire API surface.

Passing upstream.body straight to the response is the streaming trick. It's a ReadableStream, not buffered bytes, so SSE flows through the BFF chunk by chunk. Calling await upstream.text() here would silently break the playground by waiting for the full response.

Header handling in both directions. Inbound, host, cookie, and any client-supplied authorization are stripped before the real token is attached — otherwise a client could smuggle its own. Outbound, transfer-encoding and connection are dropped because they describe that connection and re-emitting them corrupts this one.

Improvement — denylist vs. allowlist

filterHeaders removes four named headers and forwards everything else, including x-forwarded-* and arbitrary client headers. An allowlist (accept, content-type, accept-encoding, user-agent, traceparent) is the safer default: with a denylist you must think of every bad header in advance; with an allowlist, anything you didn't consider is simply dropped.

4.4 Auth.js — OAuth and the token exchange

Concept — OAuth 2.0, briefly

"Sign in with Google" without Google ever telling you the password. Roughly: your app redirects to Google → the user approves → Google redirects back with a short-lived code → your server swaps that code (plus your client secret) for an access token → you call Google's userinfo endpoint with it to learn who they are.

The code round-trip exists so the token never travels through the browser's URL bar or history.

Why exchange at all? Google's token proves who you are to Google. It says nothing about your organization or role in this system. So on first sign-in the frontend posts it to the backend's /v1/oauth/exchange, which resolves the email, finds-or-creates the User and Organization, and returns a backend JWT carrying user_id, org_id, role. That JWT is what authorizes API calls afterwards.

The account guard. The jwt callback fires on every session read, but account is populated only on the first call after sign-in. Without that check you'd hit the backend on every page load.

Defect — the exchange result is never used defect

The callback stores the backend JWT as token.backendJwt. The dashboard's server actions read session.accessToken — which is only set on the failure path. So when the exchange succeeds, the actions send no token at all and every key operation returns 401. TypeScript catches it: Property 'accessToken' does not exist on type 'Session'.

Worth noting the failure fallback is also questionable — persisting the raw Google token on the session means it reaches BFF logs. Mint-then-discard is the safer pattern.

Concept — Server Actions

"use server" marks a function as server-only and RPC-callable from a client component. React generates the endpoint, the fetch, and the serialization; you write a function. Concept — discriminated unions for state

CreateKeyState is a union where status is the discriminator. Check status === "success" and TypeScript narrows the type, making key available — and making message a compile error. 5.2 lib/auth.ts — storing a token on someone's laptop

The problem. After openrouter login the token must persist. A plaintext file in the home directory is readable by every process running as that user, and gets swept into backups and dotfile repos.

Concept — the OS keychain

Every desktop OS has an encrypted credential store: Keychain on macOS, Credential Manager on Windows, libsecret/GNOME Keyring on Linux. Secrets are encrypted at rest and unlocked with the user's login. keytar is the Node binding to all three.

The catch: it's a native module needing compilation, and on a headless server, a container, WSL, or Alpine there may be no keyring daemon at all. So you need a fallback.

cli/src/repository/auth.tstrimmed
export interface CredentialStore {
  readonly kind: 'keytar' | 'encrypted-file';
  get(account?: string): Promise<string | null>;
  set(token: string, account?: string): Promise<void>;
  remove(account?: string): Promise<boolean>;
}

class EncryptedFileStore implements CredentialStore {
  private deriveKey(salt: Buffer): Buffer {
    // Master secret = OS user identity.
    const ui = userInfo();
    const material = `${ui.username}:${ui.uid}:${ui.homedir}`;
    return scryptSync(material, salt, 32);
  }

  async set(token: string, account = ACCOUNT_NAME): Promise<void> {
    const salt = randomBytes(16);
    const iv   = randomBytes(12);
    const key  = this.deriveKey(salt);
    const cipher = createCipheriv('aes-256-gcm', key, iv);
    const ct  = Buffer.concat([cipher.update(Buffer.from(token, 'utf-8')), cipher.final()]);
    const tag = cipher.getAuthTag();
    await writeFile(path, JSON.stringify({ v: 1, alg: 'aes-256-gcm', iv, tag, salt, ct }), { mode: 0o600 });
  }
}

async function loadKeytar(): Promise<CredentialStore | null> {
  try {
    const mod = await import('keytar').catch(() => null);
    if (!mod) return null;
    await keytar.findCredentials(SERVICE_NAME);   // probe — Linux without libsecret throws here
    return new KeytarStore(keytar);
  } catch { return null; }
}
Concept — AES-256-GCM and authenticated encryption

AES-256 is the symmetric cipher; GCM is the mode, and it's authenticated: besides ciphertext it produces an auth tag. On decryption, a modified ciphertext fails tag verification and throws rather than returning garbage. Without authentication an attacker can flip bits in your ciphertext and you'd never know.

The IV (initialization vector) must be random and unique per encryption — reusing an IV with the same key in GCM is catastrophic, leaking the keystream. Hence randomBytes(12) fresh every time.

Concept — key derivation with scrypt

You can't use a password as a key directly — wrong length, wrong distribution. A KDF stretches it into proper key material. scrypt, like argon2, is deliberately slow and memory-hard, so brute-forcing the input is expensive.

The salt is random per file and stored alongside the ciphertext. It isn't secret; its job is to ensure the same input never derives the same key twice, defeating precomputed tables.

Being honest about the threat model

The key material here is username:uid:homedir — not secret. Any process running as the same user can recompute it and decrypt the file. The comment in the source says exactly that: "Not bulletproof against a local attacker with the same UID — but parity with how SSH keys live on the same disk."

That's the right way to document a limitation. It protects against backups, stolen disks, and accidental dotfile commits; it does not protect against malware running as you. Stating the boundary is better engineering than implying protection you don't provide.

{ v: 1, alg: 'aes-256-gcm', … } — the format is versioned. When the scheme changes, v2 files can be read by new code while v1 files are migrated. Retrofitting a version field onto an unversioned format is painful; adding it up front is free.

Backend selection by probing. loadKeytar imports optionally, then calls a method — because on Linux without libsecret the import succeeds and the first call throws. Testing capability by using it, rather than by guessing from the platform, is the reliable approach.

Concept — field numbers are the contract

The = 1, = 2 are not defaults or ordering — they're the identifiers written into the binary encoding. Field names never appear on the wire, which is why protobuf is compact and why renaming a field is safe.

The rules that follow: never reuse a number (old code would misread new data as the old field), never change a field's type, and adding a new number is always safe — old readers skip what they don't recognize. This is how two services on different deploy schedules stay compatible.

Versioned directories — auth/v1/ — mean a breaking change ships as v2 alongside v1, with both served during migration. repeated is protobuf's list. Nested messages like RateLimitPolicy keep related fields grouped and independently evolvable.

6.2 OpenAPI and generated clients

shared/openapi/openapi.yaml (478 lines, OpenAPI 3.1) is the canonical description of the public API. FastAPI generates a schema automatically, and this project deliberately does not use it as the source of truth — because then the contract would be whatever the code happens to do, and clients could only be generated after the server was written.

Concept — contract-first vs. code-first

Code-first: write the server, generate the spec. Fast, always in sync, but the API design is an accident of implementation and breaking changes are invisible until a client breaks.

Contract-first: write the spec, generate types for everyone. The contract is reviewable in a pull request, frontend and backend can be built in parallel against it, and a breaking change shows up as a spec diff. The cost is keeping the spec current — which needs CI enforcement, or it rots.

make codegen-frontend runs openapi-typescript to produce src/repository/generated/schema.ts. Types flow from one file to every consumer, so a renamed response field becomes a compile error in the dashboard instead of an undefined in production.

7 The database

7.1 Migrations with Alembic

Concept — schema migrations

The database has structure, and that structure must change over time — in lockstep with code, across every developer's laptop, CI, staging, and production. A migration is a versioned script describing one change. Each records its ID and its parent, forming a chain; the tool tracks which have been applied in an alembic_version table and runs the rest in order.

This is source control for your schema. Without it, "works on my machine" becomes a database problem, which is much worse than a code problem.

backend-python/alembic/versions/20260426_0000_initial_schema.pytrimmed
revision = "20260426_0000"
down_revision = None

def upgrade() -> None:
    op.execute("CREATE EXTENSION IF NOT EXISTS vector")
    op.create_table("organizations",
        sa.Column("id", PG_UUID(as_uuid=True), primary_key=True),
        sa.Column("slug", sa.String(100), nullable=False, unique=True),
        …)
    op.create_index("ix_api_keys_key_lookup", "api_keys", ["key_lookup"])

    for tbl in ("model_pricing", "audit_logs", …, "organizations"):

Forward-only in production. A downgrade that drops a column destroys the data in it — there is no undo. Real recovery is a new forward migration plus a restore from backup. Keeping downgrade() for local resets while banning it in prod is the standard compromise.

IF NOT EXISTS for extensions makes the migration re-runnable. Drop order is reverse of create because foreign keys prevent dropping a parent before its children.

Concept — indexes

Without an index, finding a row means scanning every row. An index is a sorted structure (usually a B-tree) that turns that into a logarithmic lookup. The cost is space, plus slower writes since every INSERT must update every index.

So you index what you filter and join on. key_lookup is indexed and unique — that single index is what makes the two-hash scheme viable.

Defect — the missing composite index defect

usage_records has five single-column indexes. But the hottest query, aggregate_for_period, filters on org_id and a created_at range together. Postgres can combine two indexes with a bitmap scan, but a composite (org_id, created_at) is dramatically better: it seeks straight to that org's slice and walks the range in order.

Column order in a composite index matters — equality columns first, range columns last. Getting that backwards makes the index nearly useless for this query.

7.2 Money, concurrency, and one SQL statement

The single most important piece of SQL in the project.

backend-python/app/repository/credits.py
async def deduct_atomic(self, org_id: UUID, amount: Money) -> bool:
    """Atomic deduction with non-negative invariant. Returns True if deducted."""
    stmt = (
        update(orm.CreditBalance)
        .where(orm.CreditBalance.org_id == org_id)
        .where(orm.CreditBalance.available >= amount.amount)   # ← the invariant
        .values(available=orm.CreditBalance.available - amount.amount)
    )
    result = await self._session.execute(stmt)
    return result.rowcount > 0
Concept — why the naive version is broken

The obvious implementation:

balance = await get(org_id)          # reads $5
if balance.available >= amount:      # $5 >= $3 → yes
    balance.available -= amount      # computes $2
    await save(balance)              # writes $2

Two concurrent requests both read $5, both pass the check, both write $2. You delivered $6 of service and charged $3. This is a lost update, and it is the single most common concurrency bug in billing code.

Concept — why the single statement is correct

Three properties combine:

  1. The check is inside the write. WHERE available >= amount is evaluated by the database at the moment of the update, not by the application seconds earlier. There is no window between checking and acting.
  2. The arithmetic is relative. available = available - amount is computed from the current row value, not from a value the application read earlier. So it's correct regardless of what happened in between.
  3. The row lock is implicit. PostgreSQL locks the row for the duration of the UPDATE; a concurrent UPDATE to the same row waits, then re-evaluates its WHERE against the new value.

rowcount then carries the answer: 1 means it happened, 0 means the condition failed and nothing changed. One round trip, no race, no explicit locking.

The other tool: SELECT … FOR UPDATE. get_for_update() takes an explicit row lock so a genuine read-modify-write (the reserve/settle flow) is safe. Use it when the logic is too complex for one statement; prefer the conditional update when it isn't. As noted in lesson 3.13, the balance read endpoint uses it unnecessarily and should not.

NUMERIC(14, 6) is exact base-10 with 14 total digits and 6 after the point — enough for per-token pricing without float error. The database type, the Python Decimal, and the Money value object all agree; a mismatch anywhere reintroduces the rounding you were avoiding.

Concept — the three probes

Startup: "has it finished booting?" — suppresses the other two until it passes, so a slow start isn't mistaken for a failure.
Liveness: "is it alive?" — failure means restart the pod. Must never check dependencies, or a Redis outage restarts your entire fleet.
Readiness: "should it get traffic?" — failure means remove from the load balancer, no restart. This is where dependency checks belong.

Confusing liveness with readiness turns a small dependency blip into a full outage, and it's the most common Kubernetes mistake in production.

Concept — the preStop sleep

When a pod is deleted, two things happen in parallel: the endpoints controller removes it from Service backends, and the kubelet sends SIGTERM. If SIGTERM wins the race, the load balancer is still sending traffic to a shutting-down pod — visible to users as 502s during every deploy.

sleep 5 before SIGTERM lets endpoint propagation finish first. It looks like a hack; it's the standard fix, and its absence is why many teams see errors on every rollout.

Concept — requests, limits, and why there's no CPU limit

Requests are what the scheduler reserves. Limits are the hard ceiling. Exceeding a memory limit gets you OOM-killed; exceeding a CPU limit gets you throttled — the kernel simply stops running you until the next 100 ms period.

Throttling is invisible in CPU graphs and devastating for tail latency: a request that needed 2 ms of CPU can wait tens of milliseconds for its quota. For a service whose entire purpose is a low P99, that's unacceptable. Omitting the CPU limit while keeping a memory limit is a considered trade — you accept noisy-neighbour risk to protect latency — and the manifest says so in a comment.

Hardening is the Pod Security Standards "restricted" profile: non-root, read-only root filesystem, no privilege escalation, all Linux capabilities dropped, seccomp on. Writable paths are explicit emptyDir mounts. Each of these turns a container escape from likely into difficult.

Kustomize overlays layer environment differences (replica counts, resources, ingress hostnames) onto one shared base, so dev and prod cannot drift structurally — only in the values that are meant to differ.

Defect — the Celery worker crash-loops fixed

The worker manifest used to pass -A app.repository.celery.app — a dot where the actual module, app.repository.celery_app, has an underscore. The container exited immediately, Kubernetes restarted it, forever, and the same wrong path in the liveness probe meant the health check couldn't catch it. The manifests (command, args, and liveness probe) now reference the correct app.repository.celery_app; the lesson stands — a one-character path typo in a manifest fails at runtime, not at apply time, so probe commands deserve the same review as application code.

8.3 Helm, Terraform, and CI

Helm templates Kubernetes YAML so one chart serves two opposite deployments: values-prod.yaml for the hosted SaaS and values-self-hosted.yaml for air-gapped customers. Where Kustomize patches static YAML, Helm parameterizes it — this repo uses both, which is common and slightly redundant.

Concept — Infrastructure as Code

Clicking through a cloud console produces infrastructure nobody can review, reproduce, or roll back. Terraform declares the desired state in files; it computes the diff against reality and applies it. Infrastructure gets code review, version history, and a repeatable path to a second region.

The dev environment composes upstream modules: VPC across 3 AZs → EKS → RDS → ElastiCache → S3. Note single_nat_gateway = true flagged "dev only" — one NAT is cheaper but a single point of failure, so prod uses one per zone. Cost and availability traded explicitly, in a comment.

CI uses dorny/paths-filter to run only the stacks that changed — touching the frontend doesn't rebuild Go. It generates proto stubs before building (they aren't committed), runs go test -race, golangci-lint, pytest against real PostgreSQL and Valkey service containers, and the frontend suite. Separate workflows handle image builds, Trivy vulnerability scanning, and k6 load tests.

Concept — -race

Go's race detector instruments memory access at runtime and reports when two goroutines touch the same location concurrently without synchronization. It only catches races that actually occur during the run — so it's only as good as your tests — but it turns a class of bug that is otherwise nearly undebuggable into a precise report with both stack traces. Always run it in CI.
