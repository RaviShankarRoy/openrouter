This atlas answers a different question from its companions. The teardown asks what is here, the annotated codebase how does the code work, first principles why is it like this. This one asks: when a request arrives, what connections open, what travels along them, and what happens at each hop.

Three things are traced throughout. Connections — the sockets, their pools and lifetimes. Context — the four values that should follow a request across boundaries, and where each one actually survives. Time — the deadline budget as it is consumed hop by hop.

1.5 Pool arithmetic — the numbers nobody adds up

Verified — three Redis pools, and the configured size is ignored

The gateway calls redis.NewClient in three separate places — repository/auth/loaders.go:25, service/ratelimit/limiter.go:47, repository/cache/exact.go:53. Each call builds an independent connection pool to the same Redis server.

Worse, RedisConfig.PoolSize is declared in shared/config/config.go with a default of 50 and is never passed to any of them. All three inherit go-redis's default of 10 × GOMAXPROCS.

On an 8-core node that is 80 connections per pool × 3 pools = 240 connections per gateway pod, not the 50 the configuration implies. At the HPA's 200-pod ceiling that is 48,000 connections against a Redis whose own default maxclients is 10,000.

Two fixes, either acceptable: pass opts.PoolSize = cfg.Redis.PoolSize at each construction site, or — better — build one client in the composition root and inject it into all three consumers, which is what the rest of the codebase does with every other dependency.

Pod typeConnectionPer podCeiling at max replicas
gateway (5–200)Redis × 3 pools~24048,000 — exceeds Redis default maxclients
gRPC to backend1200 — multiplexed, fine
provider HTTP≤50/providerbounded per host, unbounded across providers
backend (3–50)PostgreSQL20 + 10 overflow1,500 — Postgres default max_connections is 100

The general lesson this table teaches: connection counts multiply by replica count, and autoscaling multiplies them silently. A pool size that is sensible per process becomes a denial of service against your own datastore at scale. This is the standard reason PgBouncer exists in front of PostgreSQL, and the standard reason to build one Redis client per process rather than one per consumer.

02 What propagates across a boundary

Four values should follow a request everywhere it goes. Tracing is exactly the discipline of not losing them.

2.1 The four values

ValueCarried asPurposeLost if…
Request ID X-Request-ID header Correlate log lines for one user action across services A hop doesn't forward the header
Trace context traceparent (W3C) Join spans into one waterfall; carries the sampling decision No propagator is registered, or the client isn't instrumented
Deadline In-process context / CancelToken Abort downstream work when the caller has given up A hop starts from context.Background() instead of the request context
Identity Authorization, then in-process context Authorize, attribute cost, and scope data A hop re-authenticates from scratch or drops the org scope

Each is a distinct mechanism with a distinct failure mode, and they are routinely conflated. A request ID is a string you agree to copy. A trace context is a protocol with a sampling decision baked into it. A deadline is local state that cannot cross a process boundary at all unless you serialize it — gRPC does this natively, plain HTTP does not.

Why a deadline is the odd one out

Request ID and trace context are headers: copy them and they survive. A deadline is a point in time, and the two processes may not agree on the clock. gRPC solves it by sending a relative timeout (grpc-timeout: 2S) rather than an absolute instant, so clock skew is irrelevant. Over plain HTTP there is no standard header, which is why most systems simply let each hop invent its own timeout — and why the "timeouts must shrink as you go deeper" rule has to be enforced by convention instead of by the protocol.

2.3 Where traces die, and why

Verified — the gateway produces orphan spans

Three things must be true for distributed tracing to work. This service has one of them.

  1. A tracer provider. present InitTracing builds one with an OTLP exporter and a ParentBased(TraceIDRatioBased) sampler.
  2. A registered propagator. absent otel.SetTextMapPropagator(...) is never called. Without it the SDK has no configured way to serialize or parse traceparent.
  3. Instrumented clients. absent No otelhttp.NewTransport on the provider client, no otelgrpc interceptor on the backend client.

The consequence: the gateway opens a span per request and exports it, but that span has no parent and no children. Python opens its own spans in a different trace. In Tempo you get two disconnected fragments per user action and no way to join them — which is precisely the capability distributed tracing exists to provide.

The fix is small and localized:

// shared/observability/observability.go — after building the provider
otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
    propagation.TraceContext{}, propagation.Baggage{},
))

// api/middleware/chain.go — extract from the inbound request
ctx := otel.GetTextMapPropagator().Extract(
    r.Context(), propagation.HeaderCarrier(r.Header))

// service/proxy/pool.go — wrap the provider transport
Transport: otelhttp.NewTransport(base)

// repository/auth/grpc_client.go — instrument the dial
grpc.NewClient(addr,
    grpc.WithStatsHandler(otelgrpc.NewClientHandler()), ...)
The request ID has the same gap, and it is cheaper to fix

X-Request-ID is minted, stored in the context, and written to the response — and never forwarded anywhere. So even plain log correlation stops at the gateway boundary.

Two one-line additions restore it: set the header on the outbound provider request in each adapter's NormalizeRequest, and attach it as gRPC metadata (metadata.AppendToOutgoingContext(ctx, "x-request-id", id)) on the auth call. The Python side already reads x-request-id on HTTP and binds it into every structlog line, so half the work is done.

What does work today

Deadline propagation is correct throughout the Go service. Every outbound call derives from r.Context() — the gRPC auth call adds a 2 s child deadline, the readiness probe a 2 s one, the provider call inherits the request context plus the client's own 120 s ceiling. A client that hangs up cancels the provider call, which is the single most valuable propagation behaviour for cost control.

And within each process, correlation is good: structlog contextvars bind the request ID into every Python log line for the request's duration, and the Go logger stamps it on the one line it emits.

Reading the numbers

Gateway-owned work is roughly 150 µs. Mandatory Redis round trips are 1.5 ms across three separate pools. The cold auth path adds ~5 ms. The provider takes 1.5 s — four orders of magnitude more than everything else combined.

That ratio is the argument for and against this design at once. It justifies not micro-optimizing the gateway further; it also means the three sequential Redis calls — auth, rate limit, cache — could be pipelined into one round trip, and the L1 lookup could be skipped entirely until something actually writes to it.

B Chat completion — warm, the overwhelmingly common case

Same key, same pod, within 60 s of the last request. This is what nearly all production traffic looks like.

#Where~TimeWhat happens

C Streaming completion — the connection stays open

#Where~TimeWhat happens
1ChatHandler~50 µsstream: true detected. Cache lookup skipped — streams are never cached. Sets Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive.
2Proxy.send—Response headers and status written. From this instant the response is committed — no status change, no failover.

Two connection-level defects, both on this path

1. WriteTimeout kills long streams. The server's 30 s WriteTimeout covers the entire response. A 45-second generation is severed at 30 s, mid-token, with no error the client can distinguish from a network fault. Streaming servers set WriteTimeout: 0 and rely on the request context for bounding.

2. Failover after commit corrupts the stream. Proxy.send calls WriteHeader at step 2, then streams. If the stream breaks at step 7, send returns an error and ChatCompletion's loop calls it again for the next provider — which calls WriteHeader a second time. Go logs "superfluous response.WriteHeader" and the client receives provider A's partial output concatenated with provider B's complete output. The loop must track whether the response has been committed and stop retrying once it has.

D Cache hit — the path that never runs

#Where~TimeWhat would happen
1–6middleware~1 msIdentical through rate limiting.
7C8 Redis~500 µsGET cache:l1:{hash} → hit. Entry carries body, content type, status, stored-at.
8Short circuit~20 µsX-Cache: HIT set, stored status and body written, return. No router, no breaker, no adapter, no provider.

Total: ~1.5 ms instead of 1.2 s — an 800× improvement, and the provider is not billed. This is the single highest-value path in the system.

It cannot happen

ExactCache.Put is implemented and correct. Nothing calls it. ChatHandler.Create ends with // TODO: write to cache asynchronously for non-stream success paths. The hit rate is therefore permanently zero, and connection C8 exists solely to add 500 µs to every non-streaming request.

The fix is a few lines, and the "asynchronously" in the TODO matters: the write must not block the response. Buffer the body as it is written, then go func(){ cache.Put(context.Background(), key, entry, ttl) }() after the client has been served — with context.Background() deliberately, because this is the one place you do not want the request's cancellation to apply.

E Rate limited — rejection, and the fail-open branch

#Where~TimeWhat happens
1–6middleware~5 µsThrough auth. Identity carries RateLimit.RequestsPerMinute from the cached policy.
7C7 Redis~500 µsLua returns {0, 0, reset_ms} — ZCARD reached the limit, so nothing was added to the sorted set.
8Reject~10 µsRetry-After computed from ResetAt, floored at 1 s. 429 with the OpenAI error envelope. Chain stops — no provider call, no cost.

Rejection costs ~500 µs, versus 1.2 s to serve. That asymmetry is what makes load shedding effective: you can reject far more traffic than you can serve, so shedding increases successful throughput under overload.

The branch nobody sees

If the EVAL errors — Redis down, connection exhausted, script failure — the middleware calls next.ServeHTTP and the request proceeds unlimited. The comment says "log + metric upstream"; there is no log line and no metric, and no gateway metric is recorded anywhere in the codebase.

So a Redis outage silently removes all rate limiting from a paid API, and the only externally visible signal is the provider bill. At minimum this needs a counter and an alert. Better is a degraded in-process token bucket: approximate enforcement across N pods is 5× the intended limit, which is vastly better than unbounded.

Once the breaker is open

#Where~TimeWhat happens
2′Breaker #1~100 nsOpen. Execute returns ErrOpenState immediately — the function is never invoked, no socket is touched, no 2 s timeout is waited out.
3′C9 openai~1.2 sStraight to fallback. Total latency drops from 3.2 s to 1.2 s, and the dead provider receives zero traffic.

That is the whole value of the pattern: it converts a slow failure into an instant one, so resource consumption for a dead dependency falls to zero instead of growing 120× as in-flight requests pile up.

When the chain is exhausted

If every target fails, ChatCompletion returns all providers failed: %w and the handler writes 503 with code providers_unavailable. Correct — but note what does not happen: no Retry-After is set, and no cached response is served as a last resort even though the architecture document promises "return cached response if available; else 503." The graceful-degradation story is designed and not implemented.

Also note the failover is invisible. UsageEvent has a failover_used field and a retry_count field; nothing populates them because nothing publishes the event. You cannot currently answer "how often are we failing over?"

I Stripe webhook — inbound, unauthenticated, signed

5C11 Postgres~3 ms_credit_org: org_id read from the PaymentIntent metadata — the join key attached at creation — then SELECT … FOR UPDATE and the balance incremented inside one transaction.
6200—{"received": true}. Any non-2xx makes Stripe retry with backoff for up to three days.
The idempotency gap

Stripe guarantees at-least-once delivery and will redeliver on timeout or non-2xx. This handler is not idempotent: a redelivered payment_intent.succeeded increments the balance again. The docstring says the right thing — "we never trust webhook payloads as authoritative; we re-fetch before mutating" — but _credit_org reads the amount straight from the event and credits it.

The standard fix is a processed_events table keyed by Stripe's event ID, inserted in the same transaction as the credit. A unique-constraint violation then means "already handled" and the handler returns 200 without double-crediting.

The sync.Once trap on C3

grpcAuthClient.connect() stores both the connection and the error in fields guarded by sync.Once. If the very first dial fails — backend not yet up during a rolling deploy, say — c.err is set permanently and every subsequent call returns it without retrying. The gateway then serves only what its caches hold and never recovers until the pod restarts.

In practice grpc.NewClient is lazy and rarely fails at dial time (it fails on first RPC instead), so this is latent rather than active. The robust form is to retry construction on error rather than memoizing the failure — or to rely on gRPC's own reconnect behaviour and only memoize success.

4.2 Shutdown, and the connection-draining race

Terminating cleanly is a connection problem more than a process problem. The sequence when Kubernetes deletes a gateway pod:

#Where~TimeWhat happens
1k8st=0Pod marked Terminating. Two things start in parallel: endpoint removal propagates to every node's kube-proxy, and the kubelet prepares SIGTERM.
2preStopt=0…5ssleep 5. The container keeps serving normally. This exists purely to let endpoint removal win the race — without it, the load balancer sends traffic to a shutting-down pod and users see resets on every deploy.
3SIGTERMt=5sCaught by the signal loop in main.go. Distinguished from SIGHUP, which reloads config and continues.
4cancel()t=5sRoot context cancelled → both listeners stop accepting. Existing connections are untouched.
5Shutdownt=5…35s30 s budget to drain. In-flight requests — including SSE streams — finish. New connections are refused.
6tracert=35sdefer shutdownTracer(...) flushes the batch span processor. Skipping this loses the last batch of spans.
The budgets don't line up

terminationGracePeriodSeconds: 30 starts at the moment of deletion and covers everything — the 5 s preStop plus the drain. But the code's shutdown timeout is also 30 s. So the worst case is 5 + 30 = 35 s, and Kubernetes SIGKILLs at 30 s, five seconds before the drain would have completed.

Either raise the grace period to 40 s or lower the shutdown context to 20 s. As configured, a long SSE stream in flight during a deploy is killed rather than drained — the exact failure the preStop hook was added to prevent.

Three places the ladder is not monotonic
  1. Provider 120 s vs. server write 30 s. The proxy is willing to wait four times longer than the server will let it write. A slow-but-successful provider response beyond 30 s is generated, paid for, and then discarded when the write times out.
  2. No overall request budget. Nothing caps the total time across a fallback chain. Three providers each taking 100 s is 300 s of work for a client that gave up long ago, because the failover loop never checks the remaining deadline before trying the next target. A ctx.Err() != nil check at the top of the loop would fix it.
  3. Frontend retry budget. AbortSignal.timeout(30_000) is created once and reused for every attempt, so a first attempt that consumes 30 s leaves the retries with an already-aborted signal.
What the correct shape looks like

Give the request one budget at the edge and spend it down: ctx, cancel := context.WithTimeout(r.Context(), 60*time.Second) in the handler, then before each fallback attempt check what remains and skip the attempt if it cannot plausibly finish. Every downstream call already derives from that context, so a single change at the top propagates correctly to Redis, gRPC, and the provider — which is exactly what makes context-based deadlines worth the ceremony of passing ctx everywhere.

Why tracing comes first

Items 4 through 8 are real bugs, and you could fix them today. But you would have no way to confirm any of them worked — no metric moves, no trace changes shape, no dashboard responds. Doing items 1 and 2 first is what converts every later change from "we believe this helped" into "here is the graph."

That is the whole argument of this document: a system you cannot trace is a system whose behaviour you are guessing at, however carefully it was designed.
