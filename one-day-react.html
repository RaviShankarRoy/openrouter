Read first

What one day can and can't buy you

One day will not make you an experienced React developer, and the interviewer will know within five minutes if you pretend otherwise. What one focused day can do is make you a strong engineer who reasons correctly about React — which is a different and completely respectable thing to be.

Aim at this bar: you can explain why React re-renders, write a component with state and a form from a blank file, fetch data with loading and error states, and say "I haven't used that in production, but here's how I'd approach it" without flinching. For a backend developer moving over, that's a pass.

Set up before you start

Don't burn an hour on tooling. Open codesandbox.io or stackblitz.com, pick the React template, and you're coding in thirty seconds. If you'd rather work locally: npm create vite@latest my-app -- --template react, then cd my-app && npm install && npm run dev.

The deep dives are mostly explain-it topics rather than build-it topics, so they go faster than coding blocks.

If you have ten hours, cut in this order: the GitHub search app (its lessons are already in the todo app), then HOCs (lowest yield on your list — they're largely legacy), then compress the CSS block to fifteen minutes. Never cut the JavaScript block, the drills, or lazy loading.

Your edge

Everything you already know, renamed

Three years of Java means the hard ideas are already installed — immutability, lifecycle, dependency injection, the difference between identity and equality. React mostly gives them new names. Read this table twice; it will do more for you than any tutorial.

Say this in the interview

When they ask why you're moving to frontend, the honest framing lands well: "The mental models transfer — immutable updates, lifecycle, thinking in terms of state transitions. What I've had to learn is JavaScript's runtime model and React's rendering rules." That's a sentence a senior engineer says, not a bootcamp graduate.

0:00 – 1:30

The JavaScript you actually need

Skip the language tour. These seven things appear in essentially every React file, and gaps here are what interviewers actually detect.

1 · Destructuring

// pull fields out by name — you'll see this in every component signature
const { name, age } = user;
const [first, ...rest] = [1, 2, 3];      // first = 1, rest = [2, 3]

// with a default, and renamed
const { city = "unknown", zip: postcode } = address;

2 · Spread — how you "copy with changes"

const updated  = { ...user, age: 31 };        // new object, one field changed
const appended = [...items, newItem];         // new array, one item added
const removed  = items.filter(i => i.id !== 7);

// spread is SHALLOW — nested objects are still shared references
const bad  = { ...order };                    // order.lines is the same array!
const good = { ...order, lines: [...order.lines] };

3 · Array methods — your Stream API

users.map(u => u.name);                       // stream().map().toList()
users.filter(u => u.age >= 18);               // stream().filter()
users.reduce((sum, u) => sum + u.age, 0);     // stream().reduce()
users.find(u => u.id === 3);                  // findFirst().orElse(undefined)
users.some(u => u.admin);                     // anyMatch
users.every(u => u.active);                   // allMatch

// these MUTATE — never use them on React state
items.push(x); items.sort(); items.splice(0, 1);

4 · Arrow functions

const double = n => n * 2;
const add = (a, b) => a + b;
const makeUser = name => ({ name });          // parens to return an object literal

Arrows have no this of their own — they borrow it from the surrounding scope. That's precisely why React code uses them everywhere and why old class components needed .bind(this).

5 · Closures — the one to really understand

function makeCounter() {
  let count = 0;                // captured by the returned function
  return () => ++count;         // still alive after makeCounter returns
}
const next = makeCounter();
next();  // 1
next();  // 2

This is your anonymous inner class capturing an effectively-final local — except JavaScript lets the captured variable change. Every React event handler is a closure over that render's props and state, which is the single most important sentence on this page.

6 · Truthiness and equality

// falsy values, all of them:
false, 0, -0, 0n, "", null, undefined, NaN
// everything else is truthy — including [] and {} 

1 == "1"     // true  — type coercion
1 === "1"    // false — use === always, no exceptions

null ?? "d"        // "d"  — only null/undefined trigger ??
0 ?? "d"           // 0
0 || "d"           // "d"  — || also catches 0 and "", often a bug

7 · Promises and async/await

async function loadUsers() {
  const res = await fetch("/api/users");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);   // fetch does NOT throw on 404/500
  return res.json();
}

// an async function always returns a Promise
loadUsers()
  .then(users => console.log(users))
  .catch(err => console.error(err));

// run in parallel, not one after the other
const [users, orders] = await Promise.all([loadUsers(), loadOrders()]);
Interviewers probe this

fetch only rejects on a network failure. A 404 or a 500 resolves normally with res.ok === false. Forgetting the res.ok check is the most common mistake in a live-coding fetch, and a good interviewer is watching for it.

1:30 – 2:00

The HTML and CSS floor

You will not be asked to build a pixel-perfect design. You need enough not to stall. Thirty minutes, then move on.

HTML worth knowing

Structural elements carry meaning that screen readers and interviewers both notice: header, nav, main, section, article, footer, button, form, label, input, ul/li, table. Use div and span only when nothing more specific fits. Always pair a label with its input — it's a five-second accessibility win people notice.

CSS: the box model

Every element is a box: content, then padding, then border, then margin. If you remember one CSS rule, remember box-sizing: border-box — it makes width include padding and border, which is what you intuitively expect.

Flexbox — genuinely 90% of layout

.row {
  display: flex;
  gap: 1rem;                    /* spacing between children */
  justify-content: space-between;   /* along the main axis */
  align-items: center;              /* across the main axis */
  flex-wrap: wrap;
}
.column { display: flex; flex-direction: column; gap: 0.5rem; }
.grow   { flex: 1; }              /* takes the leftover space */

Specificity, briefly: inline style beats #id beats .class beats tag. If someone asks how you'd style a React app, the honest and current answer is "CSS modules or a utility framework like Tailwind, so styles are scoped to the component rather than global."

2:00 – 4:00

The React mental model

One idea underpins everything else: your component is a function of its props and state, and React calls it again whenever either changes. You never touch the DOM. You describe what the screen should look like for the current data, and React works out the minimum set of DOM edits to get there.

Components and JSX

function Greeting({ name, children }) {
  return (
    <div className="card">
      <h2>Hello, {name}</h2>
      {children}
    </div>
  );
}

// used as a tag — capital letter is required for a component
<Greeting name="Ravi"><p>Welcome back.</p></Greeting>

JSX is not HTML — it compiles to function calls. The rules that trip people up:

  • className not class; htmlFor not for (both are reserved words in JavaScript).
  • Attributes are camelCase: onClick, onChange, tabIndex.
  • Curly braces take an expression, not a statement. A ternary works; an if does not.
  • You must return exactly one root node. Wrap siblings in a fragment: <>...</>.
  • Every tag closes, including <br /> and <img />.

Props flow down, events flow up

function Parent() {
  const [count, setCount] = useState(0);
  return <Child value={count} onIncrement={() => setCount(c => c + 1)} />;
}

function Child({ value, onIncrement }) {
  return <button onClick={onIncrement}>{value}</button>;
}

A child can never write to its parent's state. It calls a function the parent handed it. When two siblings need the same data, you move that state up to their nearest common parent — that's lifting state up, and it's a phrase worth using by name.

State

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(c => c + 1)}>+1 (safe)</button>
    </>
  );
}

Calling setCount does not change count in the current render — count is a const captured by this render's closure. It schedules a re-render, and the function runs again from the top with a fresh value. Use the updater form setCount(c => c + 1) whenever the next value depends on the previous one, because React batches updates.

The classic demonstration 
setCount(count + 1);
setCount(count + 1);   // with count = 0, ends at 1 — both read the same stale value

setCount(c => c + 1);
setCount(c => c + 1);  // ends at 2 — each receives the latest

Rendering lists

<ul>
  {users.map(u => (
    <li key={u.id}>{u.name}</li>
  ))}
</ul>

key is how React matches elements between two renders — it's the equals/hashCode of reconciliation. Use a stable id from your data. Using the array index looks fine until the list reorders or you insert at the front, at which point React reuses the wrong DOM node and component state attaches to the wrong row. That's a real bug, and it's a favourite interview question.

Conditional rendering

{isLoading && <Spinner />}
{error ? <ErrorBox message={error} /> : <List items={items} />}
{items.length === 0 && <p>Nothing here yet.</p>}
Trap

{items.length && <List />} renders a literal 0 on the page when the array is empty, because 0 is falsy but still a valid React child. Always compare explicitly: items.length > 0 && ....

Forms — controlled inputs

function LoginForm() {
  const [email, setEmail] = useState("");

  function handleSubmit(e) {
    e.preventDefault();          // stop the browser's full page reload
    console.log(email);
  }

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">Email</label>
      <input
        id="email"
        value={email}
        onChange={e => setEmail(e.target.value)}
      />
      <button type="submit">Sign in</button>
    </form>
  );
}

Controlled means React state is the single source of truth — the input displays value and reports changes upward. Uncontrolled means the DOM keeps the value and you read it with a ref when you need it. Controlled is the default answer; uncontrolled is for file inputs and integrating non-React widgets.

4:00 – 6:00

Hooks

Two rules, and interviewers do ask for them: call hooks only at the top level of a component (never inside a condition, loop, or nested function), and only from a component or another hook. React tracks hooks by call order, so a conditional hook shifts the whole list and corrupts state.

useEffect

It's for synchronising with something outside React — a network request, a subscription, a timer, the document title. Not for computing values from props.

useEffect(() => {
  const id = setInterval(() => tick(), 1000);
  return () => clearInterval(id);        // cleanup: on unmount, and before each re-run
}, []);                                   // dependency array

The dependency array is the whole game:

  • omitted — runs after every single render (rarely what you want)
  • [] — runs once after mount, cleanup on unmount
  • [a, b] — runs whenever a or b changes, compared by reference (Object.is)
The infinite loop

Because dependencies are compared by reference, an object or array literal in the array is a brand-new value every render — the effect re-runs, sets state, re-renders, and loops forever. Same for a function defined in the component body. Depend on primitives (user.id, not user), or wrap the value in useMemo/useCallback.

Fetching data — know this one cold

Almost every live-coding round is some version of this. Type it until you can produce it from memory.

function UserList() {
  const [users, setUsers]     = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);

  useEffect(() => {
    let cancelled = false;                    // guard against a late response

    async function load() {                   // the effect fn itself can't be async
      try {
        const res = await fetch("/api/users");
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        if (!cancelled) setUsers(data);
      } catch (e) {
        if (!cancelled) setError(e.message);
      } finally {
        if (!cancelled) setLoading(false);
      }
    }
    load();

    return () => { cancelled = true; };       // cleanup on unmount
  }, []);

  if (loading) return <p>Loading…</p>;
  if (error)   return <p role="alert">Couldn't load users: {error}</p>;

  return (
    <ul>
      {users.map(u => <li key={u.id}>{u.name}</li>)}
    </ul>
  );
}

Two details that earn credit: the effect callback can't be async (it must return a cleanup function, not a Promise), and the cancelled flag prevents setting state after unmount when a slow response lands late.

useReducer

The hook that will feel most familiar to you, because it's a pure function you'd be happy to unit-test: (state, action) => newState. Same signature as a fold, or an event-sourced aggregate's apply method.

const initial = { count: 0, step: 1 };

function reducer(state, action) {          // pure — no I/O, no side effects
  switch (action.type) {
    case "increment": return { ...state, count: state.count + state.step };
    case "setStep":   return { ...state, step: action.payload };
    case "reset":     return initial;
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, initial);

  return (
    <>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: "increment" })}>+{state.step}</button>
      <button onClick={() => dispatch({ type: "setStep", payload: 5 })}>step 5</button>
    </>
  );
}

When to prefer it over useState: several fields that change together, transitions where the next state depends on the previous one, or the same update logic fired from many places. The practical tell is a component with five useState calls that always change in pairs.

The argument that lands best in an interview is testability: the reducer is a plain function outside the component, so you can test every transition without rendering anything. That's the same reason you'd pull business logic out of a Spring controller.

useRef

const inputRef = useRef(null);
<input ref={inputRef} />
inputRef.current.focus();

// also: a mutable box that survives renders WITHOUT triggering one
const renderCount = useRef(0);
renderCount.current++;

Think of it as an instance field that isn't part of the render output. Changing .current never causes a re-render — that's the entire difference from state.

useMemo and useCallback

const sorted = useMemo(
  () => [...items].sort((a, b) => a.price - b.price),
  [items]
);                                     // caches a computed VALUE

const handleSelect = useCallback(
  id => setSelected(id),
  []
);                                     // caches a FUNCTION's identity

Both are optimisations, not correctness tools. The honest interview answer is: "I'd reach for them when profiling shows an expensive computation re-running, or when a stable function identity is needed to keep a memoised child from re-rendering. Sprinkling them everywhere adds cost and noise." That answer is better than an enthusiastic one.

Custom hooks

Any function starting with use that calls other hooks. It's how you share stateful logic — the composition story that replaced class inheritance.

function useDebounced(value, ms = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(t);       // cancel if value changes first
  }, [value, ms]);

  return debounced;
}

// in a component:
const [query, setQuery] = useState("");
const debouncedQuery = useDebounced(query, 400);

Context — in one minute

const ThemeContext = createContext("light");

<ThemeContext.Provider value="dark">
  <App />
</ThemeContext.Provider>

// anywhere below, at any depth:
const theme = useContext(ThemeContext);

It solves prop drilling — threading a value through five components that don't care about it. Use it for genuinely global things: theme, current user, locale. It is not a state manager, and every consumer re-renders when the value changes.

8:00 – 8:30

Lifecycle: the three phases ★★

This question is almost always phrased in class-component vocabulary even at shops that write nothing but hooks, because it's an old question that stuck. Answer it in both dialects and you look like you know the history rather than just the current API.

Mounting — the component enters the DOM

constructor → render → DOM updated → componentDidMount. This is where you kick off the first fetch, set up a subscription, or start a timer.

Updating — props or state changed

render → DOM reconciled → componentDidUpdate(prevProps, prevState). React re-runs the render and applies the diff. Guard your work here by comparing against the previous values, or you'll loop.

Unmounting — the component leaves

componentWillUnmount. Cancel timers, close sockets, abort in-flight requests. Skipping this is how you get memory leaks and "can't update state on an unmounted component" warnings.

The mapping to hooks

Class methodHook equivalent
componentDidMountuseEffect(fn, [])
componentDidUpdateuseEffect(fn, [deps])
componentWillUnmountthe function returned from useEffect
shouldComponentUpdateReact.memo(Component)
getDerivedStateFromPropsjust compute it during render — no hook needed
componentDidCatchno hook exists — error boundaries are still class-only

That last row is worth saying out loud unprompted. Error boundaries remain the one thing you cannot write with hooks; in practice people use the react-error-boundary package rather than hand-writing the class. Knowing the exception signals you've actually worked with the API rather than skimmed a table.

// one effect can express mount + update + unmount together
useEffect(() => {
  const socket = connect(roomId);            // runs on mount, and on every roomId change
  return () => socket.close();               // runs before each re-run, and on unmount
}, [roomId]);
React 18 detail worth knowing

In development, <StrictMode> deliberately mounts, unmounts, and remounts every component once — so your effects run twice and you may see two fetches. That's not a bug: it's React surfacing effects that lack proper cleanup. It doesn't happen in production. Candidates who panic about the double fetch reveal they've never read the docs; mentioning it calmly is a small, real credibility win.

8:30 – 9:00

Higher Order Components

Your notebook asks what, why, when, how — so in that order.

What

A function that takes a component and returns a new, enhanced component. It is not a React feature; it's just a pattern falling out of the fact that components are values. The closest thing you know is a decorator or a Spring AOP around-advice: wrap the target, add behaviour, delegate.

How

function withAuth(Wrapped) {
  return function Guarded(props) {
    const user = useContext(AuthContext);

    if (!user) return <LoginPrompt />;
    return <Wrapped {...props} user={user} />;    // pass everything through, plus extras
  };
}

const ProtectedDashboard = withAuth(Dashboard);

Why they existed

Before hooks there was no way to share stateful logic between components. If ten screens needed auth-checking or analytics or data-subscription, an HOC was how you avoided writing it ten times. The alternative pattern of the era was render props — same goal, different shape.

When you'd use one today

Rarely. Custom hooks replaced almost every HOC use case, with less indirection and no wrapper components cluttering the tree. You still meet them in library APIs — connect() from react-redux, withRouter, withTranslation — and in older codebases.

The answer that lands: "I'd reach for a custom hook first. HOCs solve the same problem but they nest components, so you get wrapper hell in DevTools and props can silently collide. I'd expect to read them in legacy code more than write new ones."

The gotchas, if they push

Prop name collisions between the HOC's injected props and the caller's. Static methods aren't copied to the wrapper unless you hoist them. Refs don't pass through without forwardRef. And set a displayName, or DevTools shows a tree full of anonymous wrappers.

9:00 – 9:45

Redux, RTK and Zustand ★★

You have an unusually good intuition for this one already. Redux is an event-sourced aggregate: actions are events, the reducer is the pure apply function, the store is the aggregate root holding current state. If you've ever built an event-sourced service, you've built Redux.

Why it exists

When state is needed by components far apart in the tree, passing it through props is unworkable and Context re-renders everything that consumes it. Redux gives one predictable store, updates that can only happen through explicit dispatched actions, and — because every change is a described event — a traceable history you can log, replay, or time-travel through.

How the cycle works

dispatch(action) → the reducer computes a new state from the old state plus the action → subscribed components re-render. The reducer is pure: no fetching, no randomness, no mutation. Side effects live in middleware (thunks, sagas), which is the layer that made async work fit into a synchronous model.

Redux Toolkit — what people actually write now

Plain Redux was notorious for boilerplate: action type constants, action creators, switch statements, hand-written immutable updates. RTK is the official answer and is now the default; if you say "Redux" in an interview, assume they mean RTK.

import { createSlice, configureStore } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { value: 0 },
  reducers: {
    increment: (state) => { state.value += 1; },        // looks like mutation…
    addBy:     (state, action) => { state.value += action.payload; },
  },
});

export const { increment, addBy } = counterSlice.actions;   // generated for you

export const store = configureStore({
  reducer: { counter: counterSlice.reducer },
});
// in a component
const value = useSelector(state => state.counter.value);   // subscribe narrowly
const dispatch = useDispatch();

<button onClick={() => dispatch(addBy(5))}>+5</button>
The question they'll ask about that code

"You said reducers must be pure and state immutable — why does state.value += 1 work?" Because RTK runs your reducer through Immer. You're mutating a draft proxy, and Immer produces a genuinely new immutable state from the changes you recorded. Outside createSlice, that same line would be a real bug. Knowing this distinction is a strong signal.

Zustand — the minimal alternative

import { create } from "zustand";

const useCounter = create((set) => ({
  count: 0,
  increment: () => set((s) => ({ count: s.count + 1 })),
}));

// in a component — no Provider, no dispatch, no action types
const count = useCounter((s) => s.count);
const increment = useCounter((s) => s.increment);

The store is just a hook. No provider wrapping your app, no action constants, no middleware ceremony. The trade-off is exactly what you'd expect: less structure means less traceability, which matters more on a twelve-person team than a three-person one.

When not to reach for any of it

This is the part that separates a considered answer from a memorised one. Most application state is server state — data that lives in your database and is cached in the browser. That belongs in TanStack Query or RTK Query, which handle caching, deduplication, retries and refetching. Putting server data in Redux by hand means rebuilding all of that badly.

A good closing line: "I'd start with local useState, lift it when siblings need it, use Context for genuinely global values like theme or current user, and reach for Redux Toolkit or Zustand only when there's real client-side state shared across distant parts of the app. Server data goes to a query library either way."

9:45 – 10:00

Custom hooks, with code

A custom hook is any function whose name starts with use and which calls other hooks. That naming isn't decoration — it's how the linter knows to enforce the rules of hooks inside it.

The misconception interviewers probe

Custom hooks share logic, not state. Two components calling useCounter() each get their own independent count. If you need them to share one value, that's Context or a store — not a hook. Getting this wrong is the single most common misunderstanding, so being crisp about it stands out.

When to extract one

When the same useState-plus-useEffect pairing shows up in a second component, or when a component's body has grown a chunk of logic that has nothing to do with what it renders. Same instinct as pulling a private method out of a fat service class.

// persist a value to localStorage — reads once, writes on change
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    const stored = localStorage.getItem(key);        // lazy initialiser: runs once
    return stored ? JSON.parse(stored) : initialValue;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];                          // same shape as useState
}
// the whole fetch pattern, extracted once and reused everywhere
function useFetch(url) {
  const [data, setData]       = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);

  useEffect(() => {
    const controller = new AbortController();        // cancel the real request
    setLoading(true);

    fetch(url, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(setData)
      .catch(e => { if (e.name !== "AbortError") setError(e.message); })
      .finally(() => setLoading(false));

    return () => controller.abort();
  }, [url]);

  return { data, loading, error };
}

// every consumer is now three lines
const { data, loading, error } = useFetch("/api/users");

Two details to point at while writing this: the lazy initialiser form of useState (passing a function so the expensive read runs once, not every render), and AbortController, which genuinely cancels the network request rather than just ignoring the response.

10:00 – 10:30

Lazy loading and code splitting ★★★

You marked this highest, and it's a good instinct — it's the topic where a candidate can most easily show they think about users rather than just syntax.

The problem

By default a bundler concatenates your entire application into one JavaScript file. A user who lands on the login page downloads, parses, and executes the admin dashboard, the charting library, and the rich text editor before they can type their password. On a mid-range phone that's the difference between a one-second and an eight-second start.

Code splitting, chunking, lazy loading — how the three relate

They're three views of one mechanism, and being able to separate them is exactly the depth being tested:

  • Code splitting is the strategy: break the bundle into pieces that can load independently.
  • Chunking is what the bundler does: it sees a dynamic import(), treats it as a split point, and emits a separate chunk file. Vite and webpack both do this at build time.
  • Lazy loading is the runtime behaviour: the chunk is fetched over the network only when the code path that needs it actually runs.

How, in React

import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));   // split point
const Settings  = lazy(() => import("./Settings"));

function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings"  element={<Settings />} />
      </Routes>
    </Suspense>
  );
}

lazy() takes a function returning a dynamic import() promise, and that module must have a default export. Suspense is the declarative loading boundary: while anything beneath it is still loading, React renders the fallback instead. One boundary can cover a whole region — you don't need one per component.

Where to split

Routes first — it's the highest-value split and nearly free, because users navigate one page at a time. Then heavy components that are conditionally shown: a modal, a chart, a map, a WYSIWYG editor. Then genuinely large third-party libraries.

The follow-up question

"What's the downside?" Over-splitting produces a waterfall — many small chunks fetched in sequence, each one blocked on the one before, which is slower than a single larger download. And a chunk fetched on a failed network throws, so a lazy boundary wants an error boundary above it, not just a Suspense fallback. The professional refinement is preloading on intent: call the same import() on link hover so the chunk is warm by the time the user clicks.

If they ask how you'd measure it: the bundler's own analyser (rollup-plugin-visualizer for Vite, webpack-bundle-analyzer), then Lighthouse for the user-facing numbers, watching Time to Interactive and Largest Contentful Paint.

10:30 – 11:00

Virtual DOM, reconciliation and Fiber

Most candidates can say "virtual DOM means React diffs a tree." Almost none can name the heuristics that make the diff affordable, or say what Fiber changed. That gap is your opportunity.

Reconciliation: the algorithm

Comparing two arbitrary trees is O(n³) — useless at UI scale. React gets it to O(n) by assuming two things that are almost always true of real interfaces:

  1. Different element types produce different trees. If a <div> becomes a <section>, React doesn't attempt a clever diff — it destroys the entire subtree and rebuilds it, discarding that subtree's state. Same rule when a component's type changes.
  2. Keys tell React which children are the same across renders. Without them React pairs children by position, so an insertion at the front looks like "every item changed." With stable keys it recognises a single insertion and moves the existing DOM nodes.

When the type does match, React keeps the DOM node and updates only the attributes that actually differ, then recurses into the children.

React Fiber

Fiber is the reconciler rewritten in React 16 — the same diffing rules, a completely different execution model. Before it, reconciliation was a single recursive walk that could not be interrupted. On a large tree, that walk held the one browser thread for hundreds of milliseconds and every click and keystroke queued behind it.

Fiber breaks the work into small units — one fiber node per element, held in a linked list rather than the call stack — so React can do a little work, yield to the browser to keep it responsive, and resume where it left off. Because the work is now data rather than stack frames, it can also be prioritised, paused, restarted, or thrown away.

The analogy that will make this stick

Pre-Fiber reconciliation was one long synchronous method holding the only thread. Fiber turned it into a queue of small tasks on a cooperative scheduler that yields between them. It isn't parallelism — there's still exactly one thread — it's interruptibility. A typing animation stays smooth because React can pause a big re-render mid-tree and finish it after the keystroke is handled.

Two phases

Render phase — builds the work-in-progress tree and computes the diff. Interruptible, and may be discarded or run twice, which is exactly why render must be pure and free of side effects. Commit phase — applies the DOM mutations and runs effects. Synchronous and never interrupted, so the user never sees a half-updated screen.

What Fiber unlocked

Everything marketed as "concurrent React" rests on it: Suspense, automatic batching, and the priority hooks.

const [isPending, startTransition] = useTransition();

// urgent: the input must update on this keystroke
setInput(e.target.value);

// non-urgent: the expensive filtered list can lag a frame or two
startTransition(() => setQuery(e.target.value));

useDeferredValue is the same idea in one line: it hands you a copy of a value that's allowed to lag behind, so expensive children re-render at lower priority while the input stays instant.

11:00 – 11:45

Question drills

Answer each one out loud before opening it. Speaking the answer is a different skill from recognising it, and the interview tests the first one.

What is the virtual DOM, and why does it exist?

A lightweight JavaScript object tree describing what the UI should look like. On each render React builds a new tree, diffs it against the previous one, and applies only the changed operations to the real DOM. It exists because DOM mutations are expensive and because it lets you write declarative code — describe the target state, not the sequence of edits. Closest Java analogy: Hibernate's dirty checking, where you mutate objects and the framework computes the minimal SQL.

Props versus state.

Props are passed in from the parent and are read-only inside the component — like final constructor arguments. State is owned by the component, private to it, and changing it via the setter triggers a re-render. Rule of thumb: if a value never changes inside this component, it's a prop; if the component changes it over time, it's state.

Why does React need a key on list items?

To identify which item is which across renders, so it can reuse DOM nodes and component state correctly instead of rebuilding the list. Without stable keys React falls back to position, so inserting at the front or reordering makes it reuse the wrong node — a half-typed input keeps its text but attaches to a different row. Use a stable id from your data, not the array index.

What triggers a re-render?

Three things: a state update in this component, a re-render of its parent, or a change in a Context it consumes. Note that when a parent re-renders, its children re-render by default even if their props are identical — that's what React.memo exists to short-circuit.

Why can't I mutate state directly?

React decides whether to re-render by comparing references with Object.is. todos.push(item) changes the array's contents but hands back the same reference, so React sees no change and skips the render — the screen goes stale with no error. You must produce a new object or array: setTodos([...todos, item]).

What does useEffect do, and when does it run?

It runs a side effect after the render has been committed to the screen — fetching, subscriptions, timers, imperative DOM work. Timing depends on the dependency array: no array runs it after every render, [] runs it once after mount, [a] runs it whenever a changes by reference. The function you return is the cleanup, and it runs on unmount and before each re-run.

I called setCount(count + 1) and logged count — why is it the old value?

Because count is a const captured by this render's closure. The setter doesn't reassign that variable; it schedules a re-render in which the function runs again with a new count. Updates are also batched, so two setCount(count + 1) calls in one handler both read the same stale value and you end up +1, not +2. The updater form setCount(c => c + 1) always receives the latest value.

Controlled versus uncontrolled components.

Controlled: React state holds the value, the input receives it via value and reports changes via onChange — one source of truth, easy validation. Uncontrolled: the DOM node owns the value and you read it with a ref when needed. Default to controlled; use uncontrolled for file inputs or when wrapping a non-React widget.

What are the rules of hooks, and why do they exist?

Call them only at the top level — never inside a condition, loop, or nested function — and only from a component or another hook. React associates hook state with call order, not name. Wrapping a useState in an if shifts every subsequent hook by one position and silently hands them each other's state.

What is a closure, and how does it bite you in React?

A function that keeps access to the variables of the scope it was created in — the same idea as an anonymous inner class capturing a local. In React, every handler and effect closes over that render's props and state. A setInterval registered once with [] keeps seeing the first render's values forever — the "stale closure". Fix it with the updater form of the setter, or by adding the value to the dependency array.

useMemo versus useCallback.

useMemo caches the result of a computation; useCallback caches a function's identity. useCallback(fn, deps) is exactly useMemo(() => fn, deps). Both are for performance, not correctness — reach for them when a computation is genuinely expensive or when a stable identity is needed so a memoised child or an effect dependency doesn't churn.

What is prop drilling, and how do you avoid it?

Passing a value down through several layers of components that don't use it, purely to reach a deep descendant. Fixes, in escalating order: restructure so the consumer sits closer to the source, pass the rendered element as children instead of the raw data, or use Context for genuinely global values like theme or current user.

Class components versus function components.

Classes were the original model, with lifecycle methods and this.setState. Function components with hooks are the standard since React 16.8 and are what all new code uses — the same capabilities, less boilerplate, and stateful logic composes into custom hooks instead of HOCs or render props. Be straightforward: "I've learned hooks; I'd read a class component fine but I haven't written one."

How would you handle a form with validation?

Controlled inputs with state per field or one state object; validate on blur and on submit rather than on every keystroke, so errors don't flash while the user is still typing; keep an errors object in state and render messages next to their fields; call e.preventDefault() in the submit handler and disable the button while the request is in flight. Mention that for anything sizeable you'd use React Hook Form rather than hand-rolling it.

Walk me through the component lifecycle.

Three phases. Mounting: constructor, render, DOM commit, then componentDidMount — where the first fetch or subscription goes. Updating: props or state change, render runs again, React diffs and commits, then componentDidUpdate. Unmounting: componentWillUnmount, where you cancel timers and subscriptions.

With hooks it collapses into useEffect: [] is did-mount, [deps] is did-update, and the returned function is will-unmount. Worth adding: error boundaries are the one lifecycle with no hook equivalent — componentDidCatch still requires a class.

What's a Higher Order Component, and would you use one today?

A function that takes a component and returns an enhanced one — a decorator for components. It was the pre-hooks answer to sharing stateful logic like auth checks or analytics across many screens.

Today I'd use a custom hook instead: no wrapper components in the tree, no prop collisions, no static-hoisting or ref-forwarding problems. HOCs still turn up in library APIs like connect() and in older codebases, so I'd expect to read them more than write them.

When would you introduce Redux, and when wouldn't you?

When there's genuine client-side state shared across distant parts of the tree, and the team benefits from every change being an explicit, traceable action — that's essentially event sourcing for the UI, with the reducer as the pure apply function.

I wouldn't reach for it by default. Most state is server state, which belongs in TanStack Query or RTK Query so caching, deduplication and refetching come for free. Local UI state stays in useState, cross-cutting values like theme go in Context, and Zustand covers the middle ground with far less ceremony. If I did use Redux it would be Redux Toolkit — plain Redux's boilerplate is why the reputation exists.

RTK reducers look like they mutate state. Why isn't that a bug?

Because createSlice runs the reducer through Immer. What you're mutating is a draft proxy that records your changes; Immer then produces a new immutable state from that recording. The reducer stays pure from Redux's point of view. Written outside createSlice, the same line would be a genuine bug — you'd be mutating the store and React would never see a reference change.

How would you reduce the initial bundle size of a React app?

Code splitting, starting with routes — React.lazy(() => import("./Page")) behind a Suspense boundary, so a user landing on login doesn't download the admin dashboard. Then split heavy conditional components: modals, charts, editors. The bundler turns each dynamic import() into a separate chunk at build time and the browser fetches it on demand.

The caveats matter as much as the technique: over-splitting creates a request waterfall that's slower than one larger file, and a lazy boundary needs an error boundary above it because a chunk fetch can fail. I'd verify with a bundle analyser and Lighthouse rather than guessing.

What is Suspense actually doing?

It's a declarative boundary for "something below me isn't ready yet." While any descendant is suspended — a lazy chunk still downloading, or in React 18+ a data source that's still loading — React renders the fallback instead of the subtree, then swaps in the real content when it resolves. It means loading states live in one place in the tree rather than being threaded through every component as an isLoading prop.

How does reconciliation avoid being O(n³)?

Two heuristics that hold for real UIs. First, elements of different types produce different trees — so if the type changed, React discards the whole subtree and rebuilds rather than diffing it. Second, keys identify children across renders, so a list insertion is recognised as one insertion instead of "everything shifted." Together those bring it to O(n). When types match, React keeps the DOM node and patches only the changed attributes.

What is React Fiber, and what problem did it solve?

The reconciler rewritten in React 16. The diffing rules didn't change; the execution model did. Previously reconciliation was one uninterruptible recursive walk that held the single browser thread, so a large re-render blocked every click and keystroke behind it.

Fiber represents the work as a linked list of small units instead of call-stack frames, so React can do a chunk, yield to the browser, and resume — and because the work is data, it can be prioritised, paused, or discarded. It splits into an interruptible render phase and a synchronous commit phase, which is why render must stay pure. Everything concurrent — Suspense, automatic batching, useTransition, useDeferredValue — is built on it. It's interruptibility, not parallelism; there's still one thread.

When would you use useReducer over useState?

When several pieces of state change together, when the next state depends on the previous one through non-trivial rules, or when the same transitions are dispatched from many places. The practical tell is a component with several useState calls that always update in lockstep.

The reason I like it: the reducer is a pure function living outside the component, so every transition is unit-testable without rendering anything — the same argument for keeping business logic out of a controller.

If two components use the same custom hook, do they share state?

No. A custom hook shares logic, not state — each call site gets its own independent state, exactly as if you'd written the useState inline. To genuinely share one value you need Context or a store like Zustand or Redux. This is the most common misconception about custom hooks.

How would you fetch and cache server data in a real app?

useEffect plus fetch is fine for a small case and shows you understand the mechanics, but in production I'd use TanStack Query (React Query) — it handles caching, deduplication, retries, background refetching, and loading/error states, which is a lot of correctness to rebuild by hand. Naming that trade-off signals real-world judgement, and it's a strong note to end on.

9:30 – 10:00

The traps that catch backend developers

These are the specific mistakes people make when arriving from a strongly-typed, multi-threaded, mutable-object world. Read them last so they're fresh.

  • Mutating state. items.push(x) then setItems(items) renders nothing at all. Same reference, no update, no error message.
  • Expecting the setter to be synchronous. Logging state right after setting it shows the old value, every time.
  • Index as key. Fine until the list reorders, then state attaches to the wrong row.
  • Object or array literals in a dependency array. New reference every render, effect re-runs forever.
  • Making the effect callback async. It must return a cleanup function, not a Promise. Define an inner async function and call it.
  • {count && …}. Renders a bare 0 on screen. Compare explicitly.
  • Forgetting e.preventDefault() in a submit handler — the page reloads and your state vanishes.
  • Forgetting the res.ok check after fetch. A 500 sails straight through to your success path.
  • Storing derived data in state. Compute it during render. Two sources of truth drift apart.
  • class instead of className, and == instead of ===. Small, but they're read as inexperience.

In the room

What to say, including when you don't know

You are a backend engineer with three years of shipping experience who has been learning React. That's a completely coherent story — the mistake is trying to tell a different one.

Lead with what's actually strong

API design, data modelling, testing discipline, debugging production systems, thinking in state transitions. These don't stop counting because the code now runs in a browser. When you get an open question, answer it as an engineer first and a React user second.

When you don't know something

Say so in one sentence, then show how you'd reason about it. "I haven't used useReducer in a project. From what I understand it's for state with several related fields and complex transitions — the same reason I'd reach for a state machine on the backend rather than a pile of booleans. Is that the shape of it?" That answer is worth far more than a confident wrong one, and it turns a gap into a conversation.

During live coding

  • Narrate. Silence reads as being stuck; thinking out loud reads as being methodical.
  • Ask clarifying questions first. "Should the filter persist on reload?" is a senior signal, not a stalling tactic.
  • Write the JSX skeleton first with hardcoded data, confirm it renders, then wire up state. Getting something on screen early is worth a lot.
  • Say what you'd add with more time — error states, a loading skeleton, tests, accessibility labels. It shows you know the difference between an exercise and production code.

Don't claim

Redux, Next.js, React Native, class components, or performance profiling you haven't done. One follow-up question unravels it, and losing credibility mid-interview is much more expensive than the gap you were covering.

One good question to ask them

"How does the team split work between backend and frontend — do engineers own a feature end to end?" It's a real question, it signals you're thinking about contributing, and the answer tells you whether your Java experience is an asset there or a footnote.
